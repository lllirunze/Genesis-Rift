# 《开天辟地之大地的裂变》工程目录结构

## 1. 文档目的

本文用于说明项目代码框架、各工作区职责、依赖方向与当前开发边界。

当前只建立可运行、可检查和可扩展的基础结构，不在框架阶段提前实现具体战斗、移动、事件、房间或玩家同步逻辑。

---

## 2. 技术目标

项目当前目标是局域网内运行的多人网页桌游。

推荐运行方式为：

```text
一台玩家设备
    │
    ├── 运行 Node.js 权威服务
    └── 运行或提供 React 网页
              │
              ▼
同一局域网内其他设备通过浏览器访问
```

当前技术组合如下：

| 技术 | 主要职责 |
| --- | --- |
| React | 页面、棋盘容器、玩家面板和交互界面。 |
| Vite | 前端开发服务器与构建。 |
| Node.js | 局域网权威进程。 |
| Socket.IO | 预留实时双向通信与断线重连能力。 |
| TypeScript | 跨端类型、规则核心和配置约束。 |
| Zustand | 客户端本地界面与连接状态。 |
| Vitest | 规则、随机与配置测试。 |
| npm workspaces | 管理应用和共享包。 |

当前不引入数据库、账号、云服务和游戏引擎。若棋盘动画复杂度明显提高，再评估引入Phaser。

## 3. 顶层目录

```text
Genesis-Rift/
├── apps/
│   ├── web/
│   └── server/
├── packages/
│   ├── game-core/
│   ├── game-data/
│   └── shared/
├── docs/
├── logs/                   # 运行时生成，不进入 Git
├── package.json
├── tsconfig.base.json
├── .editorconfig
├── .prettierrc.json
└── .gitignore
```

| 目录或文件 | 职责 |
| --- | --- |
| `apps/` | 可直接启动的客户端和服务端应用。 |
| `packages/` | 可被应用复用的规则、数据和协议包。 |
| `docs/` | 游戏设计、开发规范与工程说明。 |
| `logs/` | 服务端运行日志目录，由日志系统自动创建，不进入版本控制。 |
| `package.json` | npm工作区、统一命令和根开发依赖。 |
| `tsconfig.base.json` | 所有TypeScript项目共享的严格检查规则。 |
| `.editorconfig` | 编辑器基础格式。 |
| `.prettierrc.json` | 自动格式化规则。 |
| `.gitignore` | 构建产物、依赖和本地环境文件忽略规则。 |

## 4. 网页客户端

路径：

```text
apps/web/
```

当前结构：

```text
apps/web/
├── src/
│   ├── app/                # 应用入口与顶层组合
│   ├── features/           # 按玩家功能划分的界面模块
│   ├── lib/                # 浏览器侧基础适配，例如Socket客户端
│   ├── state/              # Zustand本地界面状态
│   ├── styles/             # 全局样式与主题变量
│   └── main.tsx            # React挂载入口
├── public/
│   └── assets/             # 图片、音频和字体等直接加载资源
├── index.html
├── vite.config.ts
├── tsconfig.json
└── package.json
```

网页客户端负责：

* 展示玩家有权查看的状态；
* 收集移动、行动、响应与界面输入；
* 向局域网服务提交命令；
* 展示服务端返回的权威结果；
* 管理页面、弹窗、选中和连接状态。

网页客户端不负责：

* 最终行动合法性；
* 随机结果；
* 伤害和属性公式；
* 使命完成与胜利判定；
* 其他玩家的隐藏信息。

## 5. 局域网服务端

路径：

```text
apps/server/
```

当前结构：

```text
apps/server/
├── src/
│   ├── server/             # HTTP与Socket.IO启动适配
│   ├── rooms/              # 未来的房间生命周期
│   ├── sessions/           # 未来的连接与玩家会话
│   ├── transport/          # 未来的命令和事件传输映射
│   ├── logging/            # 日志格式化、异步队列、文件切换与异常降级
│   └── index.ts            # 服务端进程入口
├── .env.example
├── tsconfig.json
└── package.json
```

当前服务端只实现：

* 监听`0.0.0.0`，允许局域网设备访问；
* `/health`健康检查；
* Socket.IO连接入口；
* 协议版本握手。

未来服务端负责：

* 创建和关闭房间；
* 绑定玩家连接与会话；
* 接收并校验玩家命令；
* 调用`game-core`执行规则；
* 按权限向客户端发送公开或隐藏事件；
* 保存对局快照、权威事件记录和运行日志。

服务端不应复制`game-core`中的游戏公式。日志文件写入属于服务端基础设施职责，`game-core`中的纯规则函数只返回业务结果，不直接访问文件系统。

## 6. 规则核心

路径：

```text
packages/game-core/
```

当前结构：

```text
packages/game-core/src/
├── core/
│   ├── command/            # 玩家或系统提交的标准命令
│   ├── event/              # 规则执行后产生的标准事件
│   ├── game/               # 游戏状态与规则引擎契约
│   └── turn/               # 完整轮次和玩家回合阶段
└── systems/
    ├── attribute/
    ├── battle/
    ├── character/
    ├── contract/
    ├── economy/
    ├── environment/
    ├── equipment/
    ├── event/
    ├── hand/
    ├── map/
    ├── mission/
    ├── movement/
    ├── npc/
    ├── random/
    └── revival/
```

规则核心必须保持：

* 不依赖React；
* 不依赖浏览器DOM；
* 不依赖Socket.IO；
* 不直接访问数据库；
* 相同输入得到相同结果；
* 所有随机结果由显式随机上下文提供；
* 所有状态修改通过命令和系统入口完成。

各系统目录目前只有占位入口，用于确定职责和依赖。后续应逐个根据设计文档补充类型、校验、纯计算、状态应用和测试。

系统内部的定义、配置与执行逻辑使用独立文件管理。例如：

```text
systems/hand/
├── hand-card-definition.ts   # 联合类型、接口与结构校验
├── hand-card-config.ts       # 允许值、默认值与可调整规则
├── hand-card-deck-state.ts   # 牌库运行时状态与操作
└── index.ts                  # 模块公开导出
```

`definition` 文件不保存允许值数组、默认数值或映射表。`config` 文件不保存玩家运行时状态，也不实现复杂业务流程。

## 7. 游戏配置

路径：

```text
packages/game-data/
```

配置包负责保存：

* 种族与身份；
* 地图与地形；
* 装备、图纸与材料；
* 手牌；
* 事件与使命；
* 天气和其他固定资源。

配置包只保存静态定义，不保存玩家当前生命、位置、手牌或对局进度。

当前`GameDataCatalog`只定义资源分类框架。正式数据加入前，应先为各类配置建立明确TypeScript类型和加载校验。

配置包内部划分为：

```text
packages/game-data/
├── data/                   # 参与规则计算的结构化配置
├── locales/
│   └── zh-CN/              # 简体中文界面与游戏字符串
└── src/                    # 配置类型、目录和加载校验
```

规则配置只保存稳定资源 ID 与字符串键。例如装备资源使用 `equip_000001`，对应本地化字符串键可以使用 `equipment.iron_sword.name`。资源 ID 与字符串键属于不同概念，实际中文名称由语言资源提供，避免规则数据与展示文案耦合。

## 8. 表现资源

路径：

```text
apps/web/public/assets/
```

当前结构：

```text
assets/
├── images/
│   ├── board/              # 地块、地形和棋盘装饰
│   ├── characters/         # 头像、单位标记及按性别与种族划分的立绘
│   ├── faith/              # 信仰外框、标识和相关表现资源
│   ├── equipment/          # 装备、图纸和材料图标
│   ├── events/             # 事件配图
│   ├── hand-cards/     # 手牌牌面与插图
│   └── ui/                 # 图标、纹理和界面装饰
├── audio/
│   ├── music/              # 背景音乐
│   └── sfx/                # 界面、战斗与环境音效
└── fonts/                  # 具有合法使用权限的网页字体
```

表现资源不参与规则计算。服务端和`game-core`只传递资源ID或资源路径，不读取图片、音频与字体内容。

所有资源文件统一使用小写英文和连字符命名。引入第三方素材时必须确认授权范围并记录来源，未经授权的影视剧截图、音乐和角色形象不得直接加入项目。

## 9. 共享协议

路径：

```text
packages/shared/
```

共享包保存客户端、服务端和规则包都需要使用的稳定定义：

* `GameId`、`PlayerId`、`TileId`等ID类型；
* 六边形`CubeCoordinate`；
* 客户端到服务端的事件类型；
* 服务端到客户端的事件类型；
* 协议版本。

共享包不能包含：

* React组件；
* Node.js服务启动代码；
* 具体游戏规则；
* 数据库模型；
* 只属于单端的内部状态。

---

## 10. 依赖方向

项目依赖方向固定为：

```text
apps/web ───────────────► packages/shared
    │
    └──────────────────► packages/game-core（仅公开查询和类型）

apps/server ────────────► packages/shared
    ├──────────────────► packages/game-data
    └──────────────────► packages/game-core

packages/game-core ─────► packages/shared
packages/game-data ─────► packages/shared
```

禁止以下反向依赖：

* `game-core`依赖`apps/web`；
* `game-core`依赖`apps/server`；
* `shared`依赖任何应用；
* `game-data`直接调用服务端网络；
* 网页客户端导入服务端内部文件。

## 11. 状态与通信边界

未来玩家操作建议采用以下流程：

```text
React收集玩家意图
        │
        ▼
生成共享协议命令
        │
        ▼
Node.js服务端检查会话与权限
        │
        ▼
game-core校验并执行规则
        │
        ▼
生成标准游戏事件
        │
        ▼
服务端按权限过滤事件
        │
        ▼
React更新显示状态
```

客户端不能提交“我的攻击未被闪避”“我获得了传说装备”等最终结果，只能提交“我要攻击该目标”“我要开启该宝箱”等行动意图。

## 12. 当前不实现的内容

框架阶段暂不实现：

* 房间创建与加入；
* 玩家名称、重连和离线托管；
* 地图生成和六边形棋盘；
* 回合、移动和战斗规则；
* 手牌、装备、事件和使命；
* 存档与数据库；
* 公网服务器和账号系统；
* 聊天、语音和观战；
* Phaser动画层。

这些内容应在相应设计确认后，逐步接入现有边界，而不是提前堆入应用入口。

## 13. 推荐开发顺序

后续建议按照以下顺序推进：

1. 完成共享ID、坐标、命令和事件类型。
2. 在`game-data`建立配置类型与校验入口。
3. 在`game-core`实现六边形地图基础能力。
4. 实现最小对局状态与回合推进。
5. 增加服务端单房间内存状态。
6. 增加客户端连接和只读棋盘显示。
7. 接入移动、事件和使命形成最小可玩循环。
8. 再扩展战斗、装备、昼夜和其他模块。

每一步都应同时包含类型、实现、测试和对应文档更新。

---

## 14. 设计原则

工程结构遵循以下原则：

* 规则独立。 游戏逻辑不绑定React、Socket.IO或数据库。
* 服务端权威。 局域网房主维护最终状态和随机结果。
* 配置分离。 静态内容与运行时实例分别管理。
* 协议稳定。 跨端事件通过共享类型与版本控制。
* 模块清晰。 目录按照业务职责划分，不堆入通用工具。
* 先小后大。 当前只提供单房主、内存状态所需的轻量基础。
* 可测试。 规则核心不依赖界面，可以使用固定输入独立验证。
* 可扩展。 后续数据库、Phaser或公网服务通过适配层接入。

当前框架的意义是先稳定边界，而不是提前填满逻辑。只要持续遵循单向依赖和权威状态流程，后续系统可以逐步实现，而无需推翻整个工程结构。
