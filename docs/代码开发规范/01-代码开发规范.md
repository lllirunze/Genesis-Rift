# 《开天辟地之大地的裂变》代码开发规范

## 1. 规范目标

本规范用于统一项目中的代码风格、命名方式、目录组织、数据定义和开发流程，降低代码理解与维护成本。

本规范适用于游戏核心逻辑、服务端、前端、配置工具、自动化测试及相关脚本。具体工具配置可以随着技术方案调整，但本规范定义的职责边界与业务约束应保持稳定。

项目开发遵循以下基本原则：

1. 代码首先是写给人看的，其次才是交给计算机执行的。
2. 相同类型的问题采用相同的解决方式。
3. 优先保证代码清晰，不为缩短代码而牺牲可读性。
4. 游戏规则、数值配置与程序执行逻辑相互分离。
5. 随机、属性、战斗、移动、回合等核心规则由统一模块负责。
6. 不在多个位置重复实现同一条规则。
7. 客户端只表达玩家意图，权威逻辑负责合法性校验与最终结算。
8. 核心行为应支持测试、日志、存档与结果复现。

当代码实现与设计文档发生冲突时，应先确认当前有效规则，再同步修改实现、配置、测试与文档，不得让冲突长期存在。

## 2. 命名规范

### 2.1 基本要求

命名应满足以下要求：

* 使用具有实际含义的英文单词。
* 避免使用拼音及中英文混合命名。
* 避免使用含义不明确的缩写。
* 名称应简洁，但不能因过度简化而丢失含义。
* 同一概念在整个项目中使用同一个名称。
* 代码术语应与设计文档保持一致。

推荐：

```text
playerHealth
movementCost
currentRound
equipmentSlots
calculateDamage
```

不推荐：

```text
ph
mc
num
data1
doIt
wanJiaXueLiang
```

只有公认缩写可以直接使用，例如：

```text
id
url
api
ui
npc
hp
mp
json
```

业务中已经确定的概念不得随意替换。例如，项目使用“身份（Identity）”描述法师、游侠、盗贼等角色定位，不再额外建立一套“职业（Profession）”代码模型；项目统一使用“手牌（Hand Card）”描述玩家可获得和使用的牌，并使用“牌库（Deck）”描述尚未抽取的手牌集合。

### 2.2 变量、参数与函数

变量、参数和函数使用小驼峰命名法（camelCase）。

```ts
const playerName = "player-1";
const maximumHealth = 100;

function calculateMovementCost(): number {
  // ...
}

function getPlayerById(playerId: PlayerId): Player | undefined {
  // ...
}
```

函数名称通常采用“动词 + 名词”的形式：

```text
createPlayer
removeModifier
calculateDamage
drawWeatherCard
moveCharacter
refreshNpc
```

布尔值应使用能够表达判断含义的前缀：

```text
isAlive
isVisible
hasWeapon
canMove
shouldRefresh
```

避免使用：

```text
alive
visible
moveFlag
statusFlag
```

### 2.3 类、接口、枚举与类型

类、接口、枚举和类型使用大驼峰命名法（PascalCase）。

```ts
class PlayerCharacter {}

interface DamageResult {}

type CharacterId = string;

enum CharacterState {
  Normal = "normal",
  KnockedDown = "knockedDown",
  Dead = "dead",
  Soul = "soul",
}
```

TypeScript 接口不添加无实际意义的 `I` 前缀。

推荐：

```ts
interface Player {}
```

不推荐：

```ts
interface IPlayer {}
```

### 2.4 常量

真正不会改变的模块级或全局常量使用全大写蛇形命名法（UPPER_SNAKE_CASE）。

```ts
const RATE_BASE = 10_000;
const MILLISECONDS_PER_SECOND = 1_000;
const CONFIG_ID_SEPARATOR = ".";
```

普通局部变量即使使用 `const` 声明，也仍然使用小驼峰命名。

```ts
const currentPlayer = getCurrentPlayer();
const damageResult = calculateDamage(context);
```

不要因为变量使用了 `const` 就全部写成大写。

具有游戏设计含义且可能调整的数值，应优先来自配置，而不是仅作为代码常量存在。

### 2.5 文件与目录

目录和代码文件统一使用小写短横线命名法（kebab-case）。

```text
battle-system/
character-system/
random-system/
map-system/

damage-calculator.ts
player-character.ts
attribute-modifier.ts
random-service.ts
```

配置文件根据内容命名：

```text
race-config.json
identity-config.json
equipment-config.json
hand-card-config.json
weather-config.json
```

项目内不得混合使用以下文件命名方式：

```text
playerCharacter.ts
PlayerCharacter.ts
player-character.ts
```

本项目统一使用：

```text
player-character.ts
```

### 2.6 稳定ID

配置ID和运行时实例ID使用小写英文，并采用稳定的命名空间结构。

```text
identity.ranger
race.human
equipment.weapon.wooden-sword
hand-card.combat.precise-strike
event.common.abandoned-camp
```

代码中的类型名使用 `Id`，例如 `playerId`、`eventId`、`configId`。配置字段统一使用 `id`，不混用 `ID`、`Id` 和 `identifier`。

## 3. 目录组织规范

代码目录按照业务模块划分，而不是简单按照控制器、服务、模型等文件类型集中堆放。

推荐基础结构如下：

```text
src/
├── core/
│   ├── game/
│   ├── turn/
│   ├── command/
│   └── state/
├── systems/
│   ├── character/
│   ├── attribute/
│   ├── battle/
│   ├── movement/
│   ├── map/
│   ├── hand/
│   ├── equipment/
│   ├── economy/
│   ├── event/
│   ├── mission/
│   ├── npc/
│   ├── environment/
│   ├── revival/
│   └── random/
├── data/
│   ├── races/
│   ├── identities/
│   ├── equipment/
│   ├── hand-cards/
│   ├── events/
│   ├── missions/
│   └── maps/
├── shared/
│   ├── constants/
│   ├── types/
│   ├── errors/
│   └── utils/
├── ui/
└── tests/
```

各目录职责如下：

| 目录 | 职责 |
| --- | --- |
| `core` | 管理对局、完整轮次、玩家回合、命令执行与权威游戏状态。 |
| `systems` | 实现角色、数值、战斗、地图、移动等具体业务规则。 |
| `data` | 保存身份、种族、装备、手牌、事件与使命等静态配置。 |
| `shared` | 保存真正跨业务通用的类型、常量、错误与无业务工具。 |
| `ui` | 展示状态、收集输入并呈现权威逻辑返回的结果。 |
| `tests` | 保存自动化测试、测试资源与固定种子场景。 |

具体工程可以根据前后端拆分方式增加 `server`、`client`、`packages` 或 `apps`，但业务模块边界应保持一致。

不得将所有代码都放入 `utils`、`common`、`service` 或 `manager`。只有不包含具体业务含义、没有外部状态且可被多个模块复用的函数，才适合放入通用工具目录。

## 4. 模块职责规范

### 4.1 单一职责

一个类、函数或模块只负责一类工作。

例如，伤害计算函数只负责根据输入生成结果：

```ts
function calculateDamage(input: DamageInput): DamageResult {
  // 只进行伤害计算，不修改外部状态。
}
```

它不应同时负责：

* 修改玩家生命值。
* 播放界面动画。
* 保存数据库。
* 发送网络消息。
* 推进游戏回合。

推荐拆分为：

```ts
const result = calculateDamage(input);

applyDamage(targetId, result);
publishBattleEvent(result);
renderDamageAnimation(result);
```

### 4.2 禁止跨模块直接修改内部数据

不同系统通过公开方法、命令或领域事件交互，不能直接修改其他模块维护的内部状态。

不推荐：

```ts
player.attributes.health -= damage;
player.state = "dead";
```

推荐：

```ts
battleService.applyDamage(playerId, damage);
```

统一入口应保证生命值边界、濒死状态、正式死亡及后续触发均由正确模块处理。

### 4.3 核心规则只能存在一份

同一条游戏规则不能在多个模块中重复实现。

例如，移动成本只能由移动系统统一计算：

```ts
movementService.calculateMovementCost(context);
```

界面层不能自行复制规则：

```ts
// 不推荐：界面复制了泥泞地形规则。
const cost = terrain === "mud" ? 2 : 1;
```

前端可以调用相同的纯计算接口展示预计结果，但最终执行仍必须由权威逻辑重新校验。

### 4.4 依赖方向

业务模块不得形成循环依赖。

推荐依赖方向为：

```text
UI / Network
      │
      ▼
Command / Application
      │
      ▼
Domain Systems
      │
      ▼
Shared Types / Data / Infrastructure Interfaces
```

底层数值、随机和类型模块不得反向依赖界面、网络或具体页面组件。

## 5. 函数编写规范

### 5.1 函数保持简短

一个函数应完成一个明确动作。

```ts
function executeAttack(command: AttackCommand): AttackResult {
  validateAttack(command);
  const damage = calculateDamage(command);
  applyAttackDamage(command.targetId, damage);
  return createAttackResult(command, damage);
}
```

出现以下情况时，应考虑拆分函数：

* 超过约 `50` 行。
* 出现多层嵌套。
* 同时执行多个不相关操作。
* 函数名称无法准确概括全部行为。
* 需要大量注释解释控制流程。

行数不是强制限制，职责清晰度才是判断依据。

### 5.2 参数数量不宜过多

参数超过 `3` 至 `4` 个时，应考虑使用参数对象。

不推荐：

```ts
calculateDamage(
  attacker,
  target,
  weapon,
  skill,
  weather,
  terrain,
  modifiers,
);
```

推荐：

```ts
interface DamageContext {
  attacker: Character;
  target: Character;
  weapon?: WeaponInstance;
  skill?: SkillConfig;
  weather?: WeatherState;
  terrain?: TerrainType;
  modifiers: readonly AttributeModifier[];
}

calculateDamage(context);
```

### 5.3 避免隐藏副作用

名称以 `get`、`find`、`calculate`、`check`、`validate` 开头的函数，原则上不修改游戏状态。

```ts
calculateDamage(context);
validateMove(command);
```

修改状态的函数使用明确动作名称：

```text
applyDamage
consumeItem
removeEquipment
advanceRound
```

### 5.4 尽早返回

使用提前返回减少嵌套。

```ts
function canPlayerMove(player: Player): boolean {
  if (player.state === CharacterState.Dead) {
    return false;
  }

  if (player.remainingMovement <= 0) {
    return false;
  }

  return true;
}
```

避免将主要逻辑包裹在多层条件分支中。

### 5.5 纯计算优先

属性、伤害、移动成本、使命条件和权重等计算应优先编写为纯函数。

相同输入必须得到相同输出，函数不读取未显式传入的可变全局状态，也不在计算过程中修改输入对象。

## 6. 数据与配置规范

### 6.1 配置与代码分离

种族、身份、装备、手牌、事件、使命和天气等固定内容保存在配置资源中，不应全部写死在程序逻辑里。

```json
{
  "id": "identity.ranger",
  "name": "游侠",
  "primaryAttributeAdjustments": {
    "strength": 0,
    "constitution": 0,
    "spirit": -1,
    "agility": 2,
    "insight": -1
  }
}
```

代码负责加载、校验并执行配置：

```ts
const identity = identityRepository.getById(identityId);

characterCreationService.applyIdentityAdjustments(character, identity);
```

配置驱动不代表所有逻辑都使用无类型字符串表达。复杂流程仍应由稳定代码实现，配置只提供规则参数、条件与标准效果组合。

### 6.2 所有配置必须具有稳定ID

游戏对象不能只依赖中文名称进行识别。

```json
{
  "id": "equipment.weapon.wooden-sword",
  "name": "木剑"
}
```

代码使用：

```ts
equipment.id;
```

界面显示：

```ts
equipment.name;
```

配置ID投入使用后原则上不得修改。确需修改时，必须提供存档迁移与旧ID映射。

### 6.3 同类配置字段统一

同类配置使用一致的数据结构和字段名称。

例如，运行时属性修饰统一使用偏移量概念：

```ts
interface DynamicAttributeOffsetConfig {
  id: string;
  sourceId: string;
  primaryDynamicOffset: Partial<Record<PrimaryAttributeType, number>>;
  derivedDynamicOffset: Partial<Record<DerivedAttributeType, number>>;
  duration?: EffectDuration;
}
```

不要在不同模块中分别使用以下字段表达相同概念：

```text
addValue
offset
bonus
increase
changeValue
```

本项目属性修正统一采用 `Offset`，不能由单个装备或状态自行增加乘法、覆盖等未在数值系统中定义的普通运算类型。

### 6.4 禁止魔法数字和魔法字符串

不推荐：

```ts
if (player.health <= 0) {
  player.state = 2;
}

if (weatherCard === "A") {
  duration = 8;
}
```

推荐：

```ts
if (player.health <= MINIMUM_HEALTH) {
  player.state = CharacterState.KnockedDown;
}

if (weatherCard.rank === CardRank.Ace) {
  duration = weatherConfig.specialWeatherDuration;
}
```

具有游戏设计含义的数值应来自配置或命名常量。

### 6.5 配置校验

所有外部配置在进入运行时前必须完成结构与业务校验，包括：

* 必填字段是否存在。
* ID是否唯一且格式正确。
* 枚举值和引用ID是否有效。
* 数值是否满足整数与边界规则。
* 权重、持续时间与资源数量是否合法。
* 使命、事件与效果组合是否存在明显冲突。

无效配置应在启动、构建或资源导入阶段直接报告，不应等到对局中途才静默失败。

## 7. 类型与状态规范

### 7.1 优先使用明确类型

避免滥用 `any`。

不推荐：

```ts
function handleEvent(data: any): void {}
```

推荐：

```ts
interface EventContext {
  playerId: PlayerId;
  position: MapPosition;
  round: number;
}

function handleEvent(context: EventContext): EventResult {}
```

无法确定的外部输入应先使用 `unknown`，完成校验后再转换为业务类型。

### 7.2 有限状态使用枚举或联合类型

不推荐：

```ts
player.state = "down";
player.state = "dead";
```

推荐：

```ts
type CharacterState = "normal" | "knockedDown" | "dead" | "soul";
```

若枚举需要跨网络、存档与配置使用，应显式定义稳定字符串值。

### 7.3 不使用多个布尔值表示同一状态

不推荐：

```ts
isAlive: boolean;
isDead: boolean;
isKnockedDown: boolean;
```

这些字段可能同时出现互相矛盾的值。

推荐：

```ts
state: CharacterState;
```

只有真正彼此独立的条件才分别使用布尔值。

### 7.4 区分静态配置与运行时实例

```ts
interface EquipmentConfig {
  id: EquipmentConfigId;
  name: string;
  derivedStaticOffset: Partial<Record<DerivedAttributeType, number>>;
}

interface EquipmentInstance {
  instanceId: EquipmentInstanceId;
  configId: EquipmentConfigId;
  ownerId?: PlayerId;
  durability?: number;
}
```

同一种木剑可以共用一份配置，但每一把实际物品都拥有独立实例ID与运行时状态。

### 7.5 只读输入

计算函数和查询接口的输入优先使用 `readonly`，避免调用链中的意外修改。

```ts
function calculateDamage(context: Readonly<DamageContext>): DamageResult {}
```

需要修改状态时，应由状态管理入口创建新状态或执行受控变更。

### 7.6 地图坐标类型

地图位置统一使用尖顶六边形立方体坐标：

```ts
interface CubeCoordinate {
  readonly x: number;
  readonly y: number;
  readonly z: number;
}
```

所有合法坐标必须满足：

```text
x + y + z = 0
```

地图距离、环数、六方向相邻、视野和寻路必须调用地图模块的统一函数，不得在业务模块中重复实现正方形网格、像素距离或自定义方向逻辑。

立方体坐标中的`z`是二维位置坐标。地势必须通过独立的`elevation`字段表示，不能将二者混用。

## 8. 游戏状态修改规范

### 8.1 状态修改经过统一入口

生命值、元宝、装备、位置、使命和世界状态等关键数据不能被任意代码直接修改。

```ts
healthService.applyDamage(playerId, damage);
economyService.spendCoin(playerId, coinQuantity);
movementService.movePlayer(playerId, targetPosition);
equipmentService.equip(playerId, equipmentInstanceId);
```

元宝支付参数统一表示需要扣除的元宝数量。每个 `item.coin` 物品数量单位固定代表 `1` 个元宝，不设置面额或换算倍率；变量应优先命名为 `coinQuantity`，避免使用含义不明确的 `money`、`value` 或 `stackCount`。

统一入口负责：

* 参数和权限校验。
* 时机与状态校验。
* 边界处理。
* 权威状态修改。
* 后续事件发布。
* 结果与日志记录。

### 8.2 操作返回明确结果

```ts
interface MoveResult {
  success: boolean;
  playerId: PlayerId;
  from: MapPosition;
  to: MapPosition;
  movementCost: number;
  failureReason?: MoveFailureReason;
}
```

不要只返回无法解释原因的布尔值。

明确结果对象有利于界面展示、日志记录、网络同步和问题排查。

### 8.3 校验与执行分离

```ts
const validation = movementService.validateMove(command);

if (!validation.success) {
  return validation;
}

return movementService.executeMove(command);
```

前端可以调用校验接口预览：

* 是否可以执行。
* 需要多少资源。
* 为什么不能执行。
* 可能触发哪些公开规则。

最终执行时必须重新校验，不能信任客户端之前得到的预览结果。

### 8.4 原子性

一次完整操作涉及多个状态变化时，应保证全部成功或全部失败。

例如使命重塑需要同时完成元宝扣除、次数增加、原使命失效和新使命生成。若任何步骤失败，应回滚整次操作，不能只保留部分结果。

## 9. 随机系统规范

所有随机行为必须通过统一随机系统执行。

禁止直接使用：

```ts
Math.random();
```

统一接口可以提供：

```ts
randomStream.nextInt(min, max);
randomStream.pick(items);
randomStream.shuffle(items);
randomStream.rollDice(20);
```

每次随机调用必须使用明确的随机流和用途：

```ts
const weatherStream = randomManager.getStream(RandomStreamType.Weather);
const rank = weatherStream.nextInt(1, 13);
```

不同模块使用独立随机流，例如：

```text
map
weather
battle
loot
mission
npc
event
contract
```

这样可以保证：

* 每局游戏根据主种子复现。
* 一个模块增加随机调用不会影响其他模块。
* 联机客户端得到一致结果。
* 测试可以使用固定种子。
* 日志可以定位具体随机调用。

随机结果先生成并记录，再参与规则结算。不要在条件表达式中重复调用随机函数。

不推荐：

```ts
if (stream.nextInt(1, 100) <= 20) {
  // ...
} else if (stream.nextInt(1, 100) <= 40) {
  // ...
}
```

推荐：

```ts
const roll = stream.nextInt(1, 100);

if (roll <= 20) {
  // ...
} else if (roll <= 40) {
  // ...
}
```

客户端不得生成并上报命中、掉落、事件、天气、轮回或使命抽取的最终随机结果。

## 10. 数值计算规范

### 10.1 使用统一计算入口

属性、伤害、治疗、移动成本等计算分别由对应统一模块负责。

```ts
attributeCalculator.calculateDerivedAttributes(character);
damageCalculator.calculate(context);
movementCalculator.calculateCost(context);
```

界面和其他系统不得复制计算公式。

### 10.2 遵循统一属性公式

派生属性统一按照数值系统定义的顺序计算：

```text
最终基础属性输入
= 当前基础属性
+ primaryStaticOffset
+ primaryDynamicOffset

最终派生属性
= Σ（最终基础属性输入 × coefficients）
+ derivedStaticOffset
+ derivedDynamicOffset
```

随后按照对应属性配置执行边界限制与整数处理。

计算顺序不能依赖对象遍历顺序、插件加载顺序或代码碰巧执行的先后关系。代码实现必须与《06-数值系统》保持一致。

### 10.3 避免浮点误差

游戏核心数值优先使用整数。

```ts
const criticalRate = 15; // 15%
```

如果某类比例需要更高精度，应统一使用固定基数，例如万分比：

```ts
const criticalRate = 1500;
const RATE_BASE = 10_000;
```

同一类概率或比例不能同时使用 `0.15`、`15` 和 `1500` 三种单位。

### 10.4 统一取整方式

一般数值默认采用向下取整；必须支付或完整占用的成本等特殊数值，可以由对应配置明确采用向上取整。所有取整均在规定阶段通过数值系统统一执行。

```ts
Math.floor(value);
Math.ceil(value);
Math.round(value);
```

只有规则明确要求时，才能使用不同取整方式。计算过程中不得随意多次取整，也不得由界面与服务端分别采用不同规则。

### 10.5 数值边界

所有数值结果都应经过统一边界处理，包括：

* 当前生命值不能超过最大生命值。
* 资源数量不能低于允许下限。
* 移动力、视野和概率遵循各自边界。
* 非法数值、无穷值和非数字结果必须被拒绝并记录。

## 11. 注释规范

### 11.1 注释说明原因

注释应解释业务原因、边界与设计选择，不重复代码已经表达的内容。

不推荐：

```ts
// 玩家生命值减去伤害。
player.health -= damage;
```

推荐：

```ts
// 生命值保持为非负整数，避免负值影响后续濒死与轮回结算。
player.health = Math.max(0, player.health - damage);
```

### 11.2 复杂规则说明

复杂规则应通过文档注释说明输入前提和业务限制。

```ts
/**
 * 计算玩家向地图外边界进行探索的结果。
 *
 * 规则：
 * 1. 玩家本回合开始时必须位于第十环。
 * 2. 必须消耗本回合全部剩余移动力。
 * 3. 玩家不能先从内环进入第十环，再于同一回合继续越界探索。
 */
function attemptBoundaryExploration(
  context: BoundaryExplorationContext,
): BoundaryExplorationResult {
  // ...
}
```

注释不能代替清晰的代码结构。若函数需要大量注释才能解释其控制流程，应优先考虑重构。

### 11.3 TODO必须明确

推荐：

```ts
// TODO(equipment): 接入耐久度系统后，在攻击完整结算结束时扣除武器耐久度。
```

不推荐：

```ts
// TODO
// 以后再改
// 这里有问题
```

TODO应说明所属模块、缺失内容和预期接入时机；具备任务系统时，还应关联对应任务编号。

## 12. 错误处理规范

### 12.1 不静默吞掉错误

不推荐：

```ts
try {
  executeAction();
} catch {}
```

推荐：

```ts
try {
  executeAction();
} catch (error) {
  logger.error("Failed to execute player action", {
    playerId,
    actionType,
    error,
  });

  throw error;
}
```

### 12.2 使用明确业务错误

```ts
enum MoveFailureReason {
  InsufficientMovement = "insufficientMovement",
  InvalidDirection = "invalidDirection",
  BlockedTerrain = "blockedTerrain",
  PlayerKnockedDown = "playerKnockedDown",
  PlayerDead = "playerDead",
}
```

界面根据稳定错误代码转换为玩家可理解的提示。

内部异常、业务失败与玩家提示应分离，不得直接向客户端展示程序堆栈、数据库错误或内部路径。

### 12.3 区分预期失败与系统异常

玩家移动力不足、目标无效等属于可预期业务失败，应返回明确结果；配置损坏、状态不可能组合、数据库不可用等属于系统异常，应记录上下文并进入统一异常处理。

不要通过异常控制正常业务分支，也不要将真正的系统错误伪装为普通失败。

## 13. 日志规范

日志格式与保存方式分别以《14-日志系统/01-日志文档规范》和《14-日志系统/02-日志保存机制》为准。代码开发不得在其他模块重新定义日志等级、字段宽度、文件名称或切换规则。

### 13.1 日志职责边界

纯规则函数不直接写入文件，也不依赖 Node.js 文件系统或具体日志库。

`game-core` 负责返回明确的业务结果、状态变化和失败原因；服务端编排层在结果确认后，通过统一日志工具记录关键事实。这样能够保证相同输入仍然得到相同结果，并避免日志写入失败改变规则计算。

关键游戏操作应保留日志，包括：

* 玩家加入与离开游戏。
* 完整轮次和玩家回合开始、结束。
* 玩家移动与位置变化。
* 战斗、伤害、濒死与死亡结算。
* 天气牌、事件及其他随机抽取。
* 装备调整与物品变化。
* 元宝获取与消耗。
* 使命进度、完成与重塑的非敏感摘要。
* 轮回与中途加入判定。
* 世界状态与管理员操作。

日志只记录已经发生的事实，不负责保存完整游戏状态。断线恢复依赖存档快照及权威领域事件，普通文本日志仅用于调试和人工复盘。

### 13.2 统一日志入口

业务代码只提供原始字段值，不自行添加时间、中括号、字段补位或玩家名称缩写。

推荐：

```ts
logger.info({
  target: playerName,
  targetPlayerId: playerId,
  action: "Move",
  module: "MoveService",
  message: `Player entered tile (${to.x},${to.y},${to.z}).`,
  context: {
    gameSessionId,
    from,
    to,
    movementCost,
  },
});
```

不推荐：

```ts
console.log("移动成功");
console.log(player);
```

`console.error()` 仅允许日志工具在文件系统异常时作为最终降级手段使用，业务模块不得直接调用。

### 13.3 等级与功能

日志等级固定为 `TRACE`、`DEBUG`、`INFO`、`WARN` 和 `ERROR`。

日志功能必须使用日志规范维护的公共枚举，例如 `Battle`、`Move`、`Item`、`Equip`、`Random` 和 `System`，不得在业务代码中临时创造近义分类。

关键业务结果使用 `INFO`，高频算法过程使用 `TRACE` 或 `DEBUG`，可恢复异常使用 `WARN`，功能执行失败或系统异常使用 `ERROR`。

### 13.4 隐藏信息与审计记录

普通可读日志中不得记录：

* 密码和身份验证令牌。
* 完整主随机种子及可预测后续结果的随机流状态。
* 其他玩家的隐藏信仰、使命和神鬼契约内容。
* 无意义的大型对象。
* 每一帧产生的大量重复内容。
* 未脱敏的个人隐私数据。

必须用于异常处理的隐藏过程，应保存为受权限保护的权威审计记录，不能写入普通 `latest.log`，也不能直接发送给公共客户端。玩家可见的公开结果与私密结果属于界面通知，不等同于服务端文件日志。

随机日志应能够关联游戏局 ID、随机流、调用序号、用途与结果，但不得在结果生效前向无权限客户端泄露后续随机序列。

### 13.5 写入与失败处理

服务端日志统一进入异步写入队列，由单一写入者顺序保存。业务模块不得持有日志文件句柄，也不得自行创建 `logs/` 下的文件。

日志写入、切换或归档失败时，不得回滚或重复执行已经成功的游戏业务。日志工具负责执行有限降级，并避免通过自身再次记录同一错误而产生递归。

## 14. 前端交互规范

前端负责：

* 展示玩家有权查看的游戏状态。
* 收集玩家输入。
* 发送操作命令。
* 展示权威逻辑返回的结果。
* 根据公开规则提供预览与提示。

前端不能作为最终规则裁决者。

玩家操作使用命令对象表达：

```ts
interface MoveCommand {
  gameId: GameId;
  playerId: PlayerId;
  targetPosition: MapPosition;
}

interface AttackCommand {
  gameId: GameId;
  playerId: PlayerId;
  targetId: CharacterId;
  skillId?: SkillId;
}
```

不要将整个玩家对象交给操作函数任意修改。

客户端发送的 `playerId`、目标、资源数量、位置和随机结果都不能直接信任。服务端或权威核心必须根据当前会话身份与最新游戏状态重新校验。

不同玩家接收的数据必须经过权限过滤：

* 公开状态可以广播。
* 个人手牌只发送给持有者。
* 信仰、使命与神鬼契约只发送给对应玩家。
* 上帝端或内部状态不能直接复用为普通玩家响应对象。

## 15. 测试规范

以下模块必须优先编写自动化测试：

* 属性与派生属性计算。
* 伤害、治疗与生命边界。
* 移动成本、首次探索与强制位移。
* 完整轮次和玩家回合推进。
* 随机流隔离与固定种子复现。
* 装备穿戴与栏位替换。
* 濒死、正式死亡、轮回与中途加入。
* 使命生成、推进、完成与重塑。
* 元宝获取、扣除与交易原子性。
* 地图边界、道路和区域规则。
* 隐藏信息权限。
* 状态保存、加载与版本迁移。

每条核心规则至少覆盖：

1. 正常情况。
2. 边界情况。
3. 非法输入。
4. 多个效果叠加。
5. 状态冲突。
6. 固定随机种子的复现结果。
7. 无权限玩家的访问结果。

测试名称直接描述行为：

```ts
it("enters knocked-down state when health reaches zero", () => {
  // ...
});

it("rejects movement when remaining movement is insufficient", () => {
  // ...
});

it("generates the same weather sequence with the same seed", () => {
  // ...
});
```

修复缺陷时，应优先添加能够稳定复现问题的测试，再修改代码并验证测试通过。

随机测试使用固定种子，不依赖当前时间或真实系统随机源。只有种子生成器本身的安全性测试可以单独验证非确定性行为。

## 17. 代码审查规范

提交代码前，开发者应自行检查：

* 命名是否准确并与项目术语一致。
* 是否存在重复代码或重复规则。
* 是否出现魔法数字和魔法字符串。
* 是否绕过统一入口直接修改状态。
* 是否直接使用系统随机函数。
* 是否可能泄露隐藏游戏信息。
* 是否添加必要测试。
* 是否影响旧存档与配置兼容性。
* 是否存在过长函数或过深嵌套。
* 是否存在未处理异常或浮动 Promise。
* 是否形成新的循环依赖。
* 是否同步更新相关文档和配置说明。

代码审查应优先关注：

1. 规则是否正确。
2. 权限与隐藏信息是否安全。
3. 状态修改是否一致且可恢复。
4. 随机与结算是否可复现。
5. 测试是否覆盖风险。
6. 代码是否清晰并便于扩展。

格式问题原则上交由自动化工具处理，不应占据代码审查的主要时间。

## 19. 禁止事项

项目中原则上禁止以下行为：

1. 使用 `data1`、`temp2`、`obj` 等无意义名称。
2. 在界面层复制核心游戏公式。
3. 在任意位置直接修改玩家关键状态。
4. 直接使用 `Math.random()` 或其他未纳入随机系统的随机源。
5. 在代码中大量写死装备、身份、手牌、事件和使命数据。
6. 使用中文、拼音和英文混合命名。
7. 使用多个布尔字段表示同一个角色状态。
8. 捕获异常后不处理、不记录也不继续抛出。
9. 将所有公共逻辑都放入 `utils`、`common` 或 `manager`。
10. 一个函数同时处理计算、状态修改、界面和数据保存。
11. 使用显示名称作为数据唯一标识。
12. 修改已有配置ID而不考虑存档兼容性。
13. 向无权限玩家发送信仰、使命、手牌和契约等隐藏信息。
14. 未经测试直接修改核心数值公式、回合流程或随机规则。
15. 为减少代码行数而编写难以理解的复杂表达式。
16. 依赖客户端提交的随机结果或最终状态。
17. 依赖对象遍历顺序决定修饰器、事件或战斗结算结果。
18. 为单个资源绕过统一系统增加无法追踪的特殊分支。

## 20. 项目核心约定

本项目额外遵守以下约定：

1. 地图尺寸、回合规则和可调整数值参数统一从配置读取。
2. 所有配置对象和运行时实例都具有稳定ID。
3. 所有随机行为经过随机系统，并使用明确随机流。
4. 所有属性变化经过数值与属性修饰器系统。
5. 所有角色状态变化经过状态管理模块。
6. 所有玩家操作经过权限、时机和合法性校验。
7. 所有核心计算结果应支持固定输入复现。
8. 静态配置与运行时实例相互分离。
9. 普通玩家数据、个人隐藏数据与上帝端权威数据相互分离。
10. 隐藏信息只发送给拥有查看权限的玩家。
11. 管理员和上帝的规则干预必须经过公开接口并记录日志。
12. 核心游戏规则不依赖界面组件、动画或网络表现。
13. 存档、配置与网络协议包含版本信息，支持后续迁移。
14. 新增规则时同步补充设计文档、配置校验与自动化测试。
15. 计算函数与状态修改函数保持明确边界。
16. 战斗、事件与响应链完成前，不提前推进外层回合。
17. 服务端或权威核心拥有最终裁决权，客户端只提交行动意图。
18. 当实现与文档冲突时，先确认并统一规则，不允许两者长期不一致。

通过统一命名、模块边界、数据结构、权威状态入口和开发流程，可以将复杂的游戏规则稳定落实为可读、可测试、可复现并易于扩展的代码，为后续持续开发提供统一基础。
