# 《开天辟地之大地的裂变》手牌设计规范

## 1. 设计原则

所有手牌均应遵循**简单易懂、效果明确、方便结算**的设计原则。

手牌主要用于丰富玩家的临场决策，而不是替代角色成长。因此，大部分手牌应围绕战斗、探索、事件和生存等场景提供短期收益，避免出现永久性属性成长或直接影响角色养成的效果。

每张手牌应尽量只表达一个核心效果，避免一张手牌同时拥有过多机制，降低理解和结算成本。

手牌设计需要满足以下基本要求：

* 玩家阅读牌面后能够理解使用时机和预期结果
* 系统能够判断手牌是否合法使用
* 效果能够进入统一响应窗口和响应链
* 数值能够使用现有数值系统完成结算
* 持续效果能够交由状态系统管理
* 使用后能够明确进入弃牌堆或其他指定区域

手牌可以制造意外、逆转和戏剧性，但不能依赖含糊文本或临时裁定产生强度。

## 2. 基本组成

每张手牌应采用统一结构进行设计，以方便后续维护、配置与扩展。

### 2.1 必要信息

每张手牌建议包含以下信息：

| 项目 | 说明 |
| --- | --- |
| 编号 | 手牌在共享牌库中的全局唯一资源 ID，格式为 `card_` 加六位数字。 |
| 名称 | 用于程序检索、日志和调试的英文小驼峰名称。中文名称直接绘制在牌面资源图片中。 |
| 描述 | 使用正常英文句子说明手牌的主要作用。中文说明直接绘制在牌面资源图片中。 |
| 品质 | 普通、优秀、稀有、史诗或传说。 |
| 类型 | 所属手牌类型，具体类型由《03-手牌类型》统一定义。 |
| 使用时机 | `active` 表示主动使用，`response` 表示响应已有行动或效果。 |
| 响应类型 | 响应手牌能够响应的行动或效果类型；主动手牌保持为空。 |
| 使用条件 | 满足何种条件时可以使用。 |
| 作用目标 | 自身、其他玩家、NPC、地块、区域、行动、事件或其他合法目标。 |
| 核心效果 | 手牌产生的主要效果。 |
| 结算方式 | 瞬时结算或持续生效。 |
| 持续时间 | 持续效果的回合数、阶段或结束条件；瞬时效果不填写。 |
| 结算去向 | 使用后进入共享弃牌堆或返回原使用者手中。 |
| 备注 | 无法通过标准字段表达的少量补充说明，可选。 |

其中，“是否立即生效”统一通过“结算方式”表达。

瞬时结算不代表打出后立刻跳过其他玩家的响应。其含义是：

```text
手牌合法打出
↓
进入响应窗口与响应链
↓
所有玩家连续放弃响应
↓
响应窗口关闭
↓
一次性结算该牌效果
```

只有响应窗口关闭后，手牌才会进入最终结算。任何品质或类型都不能在没有明确系统规则的情况下绕过该流程。

### 2.2 信息完整原则

手牌文本必须能够回答以下问题：

* 什么时候可以使用
* 谁可以使用
* 需要满足什么条件
* 响应的是哪个行动或效果
* 选择哪个目标
* 产生什么结果
* 效果持续多久
* 使用后进入哪里

如果任意问题无法从标准字段或牌面文本中得到答案，该手牌不能进入正式配置。

### 2.3 统一设计模板

新增手牌时，建议使用以下模板：

```text
编号：
名称：
描述：
品质：
类型：
核心定位：

使用时机：
使用条件：
响应类型：
作用目标：

核心效果：
结算方式：瞬时 / 持续
持续时间：
结算去向：弃牌堆 / 手牌

获取方式：
备注：
```

“核心定位”应使用一句话说明该牌解决什么问题。“获取方式”用于帮助品质与实际稀有程度保持一致，但不直接参与手牌效果结算。

### 2.4 编号规范

所有手牌共用一套从 `card_000001` 开始顺延的全局资源 ID。

编号应遵循以下规则：

* 每张进入牌库的手牌拥有一个唯一编号
* 数字部分必须处于 `000001` 至 `999999` 范围，`000000` 不得使用
* 新增手牌从当前最大编号继续顺延
* 已删除或停用的历史编号不再分配给其他手牌
* 功能相同的多张手牌仍然分别占用不同编号
* 手牌在牌库、玩家手中和弃牌堆之间流转时始终保留原编号

例如：

| 编号 | 名称 | 说明 |
| --- | --- | --- |
| `card_000001` | sprint | 第一张疾跑。 |
| `card_000002` | sprint | 第二张疾跑，名称与作用直接复制 `card_000001`。 |
| `card_000003` | sprint | 第三张疾跑，名称与作用直接复制 `card_000001`。 |
| `card_000004` | berserk | 第一张狂暴。 |
| `card_000005` | berserk | 第二张狂暴，名称与作用直接复制 `card_000004`。 |
| `card_000006` | berserk | 第三张狂暴，名称与作用直接复制 `card_000004`。 |

本系统不再为手牌分别设置功能定义编号和运行时实例编号，程序统一通过手牌编号查找配置并记录区域流转。

### 2.5 使用时机规范

手牌的使用时机只允许以下两种类型：

| 代码值 | 说明 |
| --- | --- |
| `active` | 玩家在满足条件的合法行动阶段主动声明，不要求存在响应对象。 |
| `response` | 玩家针对一个尚未完成结算的行动或效果进行响应。 |

每张手牌只能选择一种主要使用时机。

主动手牌声明后仍需进入统一响应流程，不能因为 `timing` 为 `active` 而直接完成结算。

响应手牌必须至少配置一个响应对象。不存在合法响应对象时，该牌不能使用。

回合开始、回合结束、指定天气和指定状态等更加具体的阶段要求，统一通过使用条件表达，不新增特殊时机类型。

当前版本不保留 `special` 等兜底值。未来若出现无法由主动、响应、使用条件和响应对象共同表达的新机制，应先补充统一规则，再评估是否扩展使用时机枚举。

### 2.6 响应类型规范

响应类型用于说明一张响应手牌能够针对何种尚未完成结算的行动或效果使用。

当前统一支持以下响应类型：

| 代码值 | 说明 |
| --- | --- |
| `attack.beforeEvasion` | 攻击进行自然闪避判定前。 |
| `damage.beforeResolution` | 伤害最终扣除前。 |
| `healing.beforeResolution` | 治疗或恢复结算前。 |
| `movement.beforeResolution` | 移动结果确认前。 |
| `exploration.beforeResolution` | 探索结果结算前。 |
| `event.beforeResolution` | 事件选项或事件结果结算前。 |
| `trade.beforeResolution` | 交易正式完成前。 |
| `handCard.beforeResolution` | 另一张手牌结算前。 |
| `weather.beforeResolution` | 天气效果结算前。 |
| `status.beforeApplication` | 状态被正式添加前。 |

响应类型遵循以下规则：

* 主动手牌的响应类型必须为空
* 响应手牌必须至少配置一个响应类型
* 配置多个响应类型时，满足任意一个即可参与响应
* 同一张手牌不能重复配置相同响应类型
* 不支持 `battle.*`、`any.*` 等通配符
* 新增响应类型时，应先加入统一类型集合，再用于具体手牌

响应类型只描述当前正在等待结算的对象，不描述天气、回合阶段、角色状态或资源数量等额外限制，其他限制统一由使用条件表达。

例如：

```text
timing: response
responseTypes:
  - attack.beforeEvasion
  - damage.beforeResolution
```

表示该牌可以响应自然闪避判定或伤害结算。

### 2.7 使用条件规范

使用条件用于表示打出手牌时必须额外满足的规则。

当手牌没有额外限制时，使用条件保持为空。当同一张手牌配置多个使用条件时，必须同时满足全部条件才能使用，即统一采用“且”关系。

当前统一支持以下使用条件：

| 代码值 | 说明 |
| --- | --- |
| `turn.isOwnerTurn` | 当前为手牌所有者的回合。 |
| `turn.isStart` | 当前处于回合开始阶段。 |
| `turn.isEnd` | 当前处于回合结束阶段。 |
| `player.canMove` | 手牌使用者当前能够移动。 |
| `player.isInCombat` | 手牌使用者当前处于战斗中。 |
| `player.isDowned` | 手牌使用者当前处于击倒状态。 |
| `source.isOwnAttack` | 当前响应来源是手牌使用者发起的攻击。 |
| `target.isSelf` | 选定目标为手牌使用者自身。 |
| `target.isAlly` | 选定目标为手牌使用者的友方。 |
| `target.isEnemy` | 选定目标为手牌使用者的敌方。 |
| `weather.isRaining` | 当前天气属于降雨天气。 |
| `time.isDay` | 当前处于白天。 |
| `time.isNight` | 当前处于夜晚。 |

使用条件遵循以下规则：

* 条件编号统一使用 `namespace.camelCase` 格式
* 空条件集表示没有额外使用限制
* 多个条件之间统一采用“且”关系
* 同一张手牌不能重复配置相同条件
* 当前版本不支持“或”、“非”与嵌套条件树
* 新增条件时，应先加入统一条件集合，再用于具体手牌
* 未登记的条件编号视为配置错误，不允许进入正式牌库

例如：

```text
conditionIds:
  - source.isOwnAttack
  - player.isInCombat
```

表示该牌只能在使用者处于战斗中，且当前响应来源为其自身发起的攻击时使用。

当后续出现大量生命值比例、资源数量或距离阈值等参数化条件时，再统一扩展结构化条件参数。在此之前，不为单张手牌单独设计条件表达式。

### 2.8 目标类型规范

目标类型用于表示手牌效果能够选择哪一类游戏对象。

当手牌不需要使用者主动选择目标，或目标已由当前响应对象唯一确定时，目标类型可以保持为空。当配置多个目标类型时，选定对象满足其中任意一种类型即可，即统一采用“或”关系。

当前统一支持以下目标类型：

| 代码值 | 说明 |
| --- | --- |
| `player` | 玩家角色。 |
| `npc` | NPC。 |
| `monster` | 普通怪物、精英怪物或首领。 |
| `tile` | 单个地图地块。 |
| `area` | 一个地图区域。 |
| `item` | 背包物品或其他物品实例。 |
| `handCard` | 一张具体手牌。 |
| `event` | 当前事件或待结算事件。 |
| `action` | 当前行动或待结算行动。 |
| `status` | Buff、Debuff 或其他状态。 |

目标类型遵循以下规则：

* 空目标类型集表示不需要主动选择目标
* 多个目标类型之间统一采用“或”关系
* 同一张手牌不能重复配置相同目标类型
* `self`、`ally` 和 `enemy` 属于目标关系，应通过使用条件表达，不作为目标类型
* `allPlayers`、`randomEnemy` 等范围或选择方式不作为目标类型
* 响应类型负责确定能够响应什么，目标类型负责确定效果最终作用于什么
* 未登记的目标类型视为配置错误，不允许进入正式牌库
* 未来增加新目标类型时，应先加入统一目标类型集合，再用于具体手牌

例如，一张只能作用于自身的手牌可以配置为：

```text
conditionIds:
  - target.isSelf
targetTypes:
  - player
```

一张可以作用于玩家或 NPC 的手牌可以配置为：

```text
conditionIds: []
targetTypes:
  - player
  - npc
```

目标数量、全体目标、随机目标与目标选择顺序不由目标类型表达。当具体手牌开始需要这些能力时，再统一设计目标范围或选择方式字段。

### 2.9 效果定义规范

手牌通过效果定义说明结算时需要调用哪一项通用能力，以及该能力本次使用的具体参数。

每个效果由以下内容组成：

| 字段 | 说明 |
| --- | --- |
| `effectId` | 需要调用的通用效果类型。 |
| `parameters` | 该效果本次结算所需的数值、资源编号或其他简单参数。 |

当前统一支持以下效果：

| 效果编号 | 参数 | 说明 |
| --- | --- | --- |
| `evasion.modify` | `amount` | 修正当前目标的闪避数值，可以为正数或负数，但不能为 `0`。 |
| `damage.reduce` | `amount` | 使当前待结算伤害减少指定正整数。 |
| `health.restore` | `amount` | 恢复指定正整数的生命值。 |
| `movement.modify` | `amount` | 修正当前移动数值，可以为正数或负数，但不能为 `0`。 |
| `status.add` | `statusDefinitionId`、`stacks` | 为目标添加指定状态及正整数层数。 |
| `status.remove` | `statusDefinitionId` | 从目标移除指定状态。 |
| `weather.change` | `weatherId` | 请求天气系统切换为指定天气。 |
| `item.obtain` | `itemDefinitionId`、`quantity` | 请求物品系统发放指定正整数数量的物品。 |
| `handCard.draw` | `amount` | 从共享牌库抽取指定正整数数量的手牌。 |

例如，恢复 `5` 点生命值：

```text
effects:
  - effectId: health.restore
    parameters:
      amount: 5
```

例如，增加 `2` 点当前移动数值：

```text
effects:
  - effectId: movement.modify
    parameters:
      amount: 2
```

一张手牌可以配置多个紧密相关的效果。系统按照 `effects` 数组中的顺序依次结算，因此配置顺序属于手牌正式规则的一部分。

效果定义遵循以下规则：

* 每张手牌至少配置一个效果
* `effectId` 必须来自统一效果类型集合
* 每种效果只允许使用自身声明的参数名称与参数类型
* 数量、层数和数值修正统一使用安全整数
* 同一 `effectId` 可以在一张手牌中多次出现，用于表达不同参数或不同结算对象
* 未登记的效果编号或不合法参数视为配置错误
* 手牌系统只声明效果，不重复实现战斗、资源、移动、状态、天气或物品系统的底层逻辑
* 需要持续多个回合的效果应使用 `status.add` 生成状态，不应为即时效果随意增加持续时间参数

未来增加新效果时，应同时登记新的 `effectId`、参数结构与参数校验规则，再由对应业务系统提供实际执行能力。

### 2.10 结算去向规范

结算去向用于表示手牌完成本次结算后，其全局手牌编号应移动至哪一个区域。

当前版本仅支持以下两种结算去向：

| 代码值 | 说明 |
| --- | --- |
| `discard` | 进入所有玩家共用的弃牌堆，是大多数手牌的常规去向。 |
| `hand` | 返回原使用者手中，仅用于少量明确具有返回能力的特殊手牌。 |

结算去向遵循以下规则：

* 每张手牌必须明确配置一个结算去向
* 手牌在不满足使用条件或使用声明被取消时，仍保留在原使用者手中，不执行结算去向
* 手牌已经合法进入响应链，但其效果在结算中被抵消时，仍按配置执行结算去向
* `discard` 使用共享弃牌堆，不为每位玩家建立独立弃牌堆
* `hand` 返回的是原手牌编号，不会创建新的同名手牌
* 返回手中的手牌继续受玩家手牌上限约束
* 手牌生成的持续状态不会因手牌进入弃牌堆而消失，其后续结算由状态系统独立管理
* 当前版本不支持直接放回牌库顶部、牌库底部或永久移出游戏

未来若需要新的结算去向，应先补充对牌库回收、洗牌、存档与共享区域的影响规则，再加入正式配置集合。

## 3. 品质设计

手牌共分为五个品质：

| 品质 | 设计定位 |
| --- | --- |
| 普通 | 提供基础效果，获取相对容易，是手牌的主要组成部分。 |
| 优秀 | 拥有更好的收益、适用范围或使用灵活性。 |
| 稀有 | 具有较强的功能性或特殊机制，获取难度较高。 |
| 史诗 | 能够明显改变局部局势，多作为高级奖励出现。 |
| 传说 | 极其稀有，拥有足以影响整场游戏的重要能力。 |

品质主要影响获取难度、机制影响范围与整体价值，并不意味着高品质手牌在所有情况下都优于低品质手牌。

部分普通手牌在合适的场景下同样能够发挥关键作用。

“神话”品质仅在通用品质体系中保留层级定义，当前版本不纳入手牌设计与配置。后续若需要启用，必须先补充独立的设计目标、颜色、获取方式、效果边界与平衡规则，而不能直接将其作为高于传说的常规数值等级使用。

### 3.1 品质差异原则

品质差异可以通过以下方式体现：

* 更高的获取难度
* 更广但仍然明确的适用场景
* 更强的局部影响能力
* 更独特的系统联动
* 更稀有的目标改变或结果修正能力
* 更高的使用条件或决策成本

品质差异不应简单表现为：

* 普通牌造成 `1` 点效果，传说牌造成 `100` 点效果
* 高品质牌可以无条件取消所有行动
* 高品质牌不允许其他玩家响应
* 高品质牌永久提高角色基础属性
* 高品质牌拥有大量彼此无关的效果

### 3.2 品质与复杂度

品质越高，可以拥有更加独特的机制，但牌面复杂度仍应受到限制。

普通与优秀手牌通常只包含一个直接效果。

稀有、史诗和传说品质手牌可以拥有一个核心效果与一个紧密相关的附加效果，但不应因此形成多段递归触发或独立子系统。

传说品质代表影响力和稀有性，不代表可以破坏基础规则或跳过系统职责边界。

传说仅属于品质，不作为独立的手牌类型。传说品质手牌仍应根据核心用途归入战斗、行动、事件、干扰或生存类型。

## 4. 效果设计规范

### 4.1 单一核心效果

每张手牌应尽量只包含一个核心效果。

例如，一张用于避免伤害的手牌，可以围绕以下某一方向设计：

* 减少本次伤害
* 改变本次伤害的目标
* 为本次伤害提供护盾
* 使本次攻击重新进行闪避判定

不应在同一张普通手牌中同时加入减伤、反击、治疗、移动和抽取手牌等多个无关效果。

### 4.2 效果文本明确

效果描述应使用明确、可验证的语言。

应优先写明：

* 明确数值
* 明确目标
* 明确持续时间
* 明确触发时机
* 明确效果结束条件

避免使用以下模糊表达：

* 大幅提高
* 有概率获得较强效果
* 持续一段时间
* 对附近目标生效
* 在适当时机触发

如果“附近”“较强”“一段时间”等概念确有必要，必须在通用规则或该牌文本中给出可计算定义。

### 4.3 优先短期影响

手牌应优先修改当前回合、当前行动、当前事件或有限回合内的结果。

允许的典型效果包括：

* 修改本次攻击或防御
* 改变一次移动或探索结果
* 干预一个事件选项
* 获得有限回合的状态
* 立即恢复一定资源
* 改变一次交易或资源结算

手牌原则上不得：

* 永久增加五项基础属性
* 永久提高派生属性
* 永久增加装备栏或手牌上限
* 直接授予永久转职或身份成长
* 绕过任务系统写入永久任务进度

具有永久影响的特殊内容应由任务、角色、装备或其他长期成长系统负责，手牌最多作为触发对应系统流程的条件之一。

### 4.4 持续效果

持续多个回合或阶段的手牌必须明确：

* 持续时间
* 生效对象
* 开始时机
* 结束时机
* 是否可以叠加
* 重复获得时如何处理
* 来源消失时是否提前结束

持续效果应转化为状态或其他已有运行时对象，由对应系统管理剩余时间、层数和移除条件。

手牌进入弃牌堆后，其已经生成的持续状态仍可继续存在，直至满足结束条件。

### 4.5 随机效果

手牌应避免大量随机效果，降低不可控因素。

如果必须使用随机结果，应明确：

* 随机范围
* 候选结果
* 每个结果的权重
* 是否受到幸运值或其他属性影响
* 随机发生的具体时机

随机过程由统一随机系统负责，手牌不能自行定义含义不明的“较高概率”或“极低概率”。

### 4.6 系统联动

手牌应尽量与战斗、探索、天气、昼夜、事件、经济和其他已有系统产生联动。

例如：

* 战斗牌调用闪避、伤害和状态规则
* 探索牌读取地形、区域或视野信息
* 天气牌读取当前天气状态
* 事件牌修改一个尚未完成结算的事件
* 资源牌调用经济系统完成获取或支付

手牌只声明需要产生的效果，不重复实现其他系统的底层逻辑。

### 4.7 禁止循环触发

手牌效果不得形成无限响应、无限抽取、无限资源或无法结束的结算循环。

涉及再次使用、返回手牌、复制或触发其他手牌的效果时，必须明确次数限制、目标限制和结束条件。

## 5. 数值设计规范

手牌数值应遵循《06-数值系统》的整数、取整和边界规则。

### 5.1 整数优先

伤害、治疗、移动、资源、次数和持续回合原则上使用整数。

能够使用固定整数表达的效果，不应优先设计为百分比。

### 5.2 使用已有属性

手牌应优先读取或临时修正已有基础属性与派生属性。

临时属性修正统一通过属性修饰器实现：

| 效果 | 数值系统处理方式 |
| --- | --- |
| 临时修正五项基础属性 | 写入 `primaryDynamicOffset` |
| 临时修正派生属性 | 写入 `derivedDynamicOffset` |

效果结束后必须移除对应修饰器，不得将手牌的临时收益写入角色永久属性。

### 5.3 比例与概率

涉及比例或概率时，必须使用项目统一的整数单位，并明确：

* 计算顺序
* 取整方式
* 最小值
* 最大值
* 是否受到其他修饰器影响

手牌不应为已有闪避、暴击和幸运规则重新建立独立概率体系。

### 5.4 数值与品质

品质越高，不代表数值必须按固定倍数增长。

数值强度应与以下内容共同考虑：

* 使用条件
* 适用范围
* 目标数量
* 使用时机
* 获取难度
* 是否需要支付资源
* 是否存在明确反制方式

不能仅根据品质确定伤害、治疗或资源收益。

---

## 6. 命名规范

手牌配置中的 `name` 统一使用英文小驼峰命名法（camelCase）。该字段主要用于程序检索、日志和调试，不承担牌面展示职责。

建议采用以下命名方式：

| 命名方向 | 示例 |
| --- | --- |
| 动作类 | `sprint`、`assault`、`block`、`counterattack` |
| 道具类 | `firstAidKit`、`townPortalScroll`、`gasMask` |
| 法术类 | `miracle`、`frostBind`、`timeStop` |
| 特殊类 | `fateReversal`、`riftIntervention`、`worldTreeBlessing` |

同一系列手牌应保持统一命名风格，便于玩家记忆与识别。

命名还应遵循以下规则：

* 功能相同的多张手牌可以使用完全相同的名称
* 同名手牌的牌面内容与实际作用必须保持一致
* 不同效果不能使用完全相同的名称
* 名称使用英文小驼峰命名法（camelCase）
* 名称必须以英文小写字母开头
* 名称只允许使用英文字母和必要的数字
* 名称中不使用空格、下划线、短横线或其他标点符号
* 名称不直接堆叠品质词语，例如 `super`、`ultimate`、`legendary`
* 名称不使用无法从世界观或效果中解释的专业术语
* 名称不应暗示牌面不存在的效果
* 系列牌可以使用共同前缀或意象，但必须保留可区分部分

手牌名称不作为程序唯一标识，程序统一使用全局资源 ID 区分每张手牌。修改同名手牌时，应同步检查并更新全部对应 ID，避免同名牌出现不同规则。

中文名称不写入手牌配置，而是直接作为牌面美术内容绘制在资源图片中。程序在日志、配置校验和调试界面中只使用英文 `name` 或资源 ID 格式的 `cardId`。

### 6.1 描述规范

手牌配置中的 `description` 使用正常英文句子表达其主要作用。

描述应遵循以下规则：

* 使用完整、简洁且语义明确的英文句子
* 句子首字母使用英文大写
* 句末使用英文句号、问号或感叹号
* 不在句首或句尾保留多余空格
* 不使用中文或全角标点
* 不使用换行拼接多段说明
* 功能相同的同名手牌复制完全相同的描述

例如：

```text
Increase movement by 2 for this action.
Reduce the incoming damage by 3.
Draw one hand card from the shared deck.
```

中文效果说明不写入 `description`，而是直接绘制在对应牌面资源图片中。

## 7. 新增手牌检查流程

新增手牌时，应按照以下流程进行设计：

```text
明确使用场景
↓
确定核心效果
↓
确定手牌类型
↓
确定使用时机与响应对象
↓
确定作用目标
↓
确定数值与持续时间
↓
确定品质与获取方式
↓
检查响应、叠加与循环风险
↓
完成牌面文本
```

进入正式配置前，应至少确认：

* 是否只有一个明确核心效果
* 是否能够判断合法使用时机
* 是否明确响应对象与作用目标
* 是否优先产生短期影响
* 是否使用已有属性和系统规则
* 是否明确持续时间与结束条件
* 是否明确结算去向
* 是否可能形成无限响应或资源循环
* 品质是否与获取难度和影响能力匹配
* 名称是否符合统一规范
* 牌面文本是否能够独立理解

---

## 8. 后续扩展

新增手牌时，应优先考虑是否能够丰富玩家的策略选择，而不是单纯提高数值。

鼓励设计具有不同使用场景的手牌，使玩家能够根据战斗、探索、天气、事件和副本等不同环境灵活选择，而不是始终依赖少数几张高品质手牌。

后续所有新增手牌均应遵循本规范进行设计，以保证整个手牌系统风格统一、规则一致，并具备良好的可维护性。

五类手牌的具体职责、使用场景和示例将在 [《03-手牌类型》](03-手牌类型.md) 中详细说明。
