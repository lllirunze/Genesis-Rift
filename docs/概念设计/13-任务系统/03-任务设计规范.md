# 《开天辟地之大地的裂变》任务设计规范

## 1. 设计目标

任务设计规范用于统一《开天辟地之大地的裂变》中所有任务（Quest）的数据结构、命名方式、目标配置、奖励规则与运行边界。

所有新增任务均应遵循本规范进行设计，避免不同任务之间出现字段结构不一致、完成条件含糊、奖励失衡或需要单独编写运行逻辑的问题。

任务设计遵循以下基本目标：

* 所有任务使用统一的静态定义结构。
* 所有玩家任务实例使用统一的运行时状态结构。
* 任务目标、条件与奖励优先通过配置组合实现。
* 任务系统只管理任务流程，不重复实现其他系统的业务逻辑。
* 新增任务原则上不修改任务系统底层框架。
* 无法由现有目标与奖励类型表达的内容，应先扩展公共能力，再配置具体任务。

任务规范的核心思想可以概括为：

**通过稳定框架管理任务流程，通过资源配置持续扩充任务内容。**

---

## 2. 任务数据结构

任务配置与玩家运行时状态必须分离。

任务静态定义用于描述所有对局共享且不会随游戏过程改变的规则；玩家任务实例只保存某位玩家在当前对局中的领取、进度与生命周期状态。

### 2.1 任务静态定义

每项任务静态定义建议包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `questId` | 全局唯一且稳定的任务定义标识。 |
| `name` | 向玩家展示的任务名称。 |
| `description` | 任务背景、内容与必要说明。 |
| `publisher` | 发布任务的 NPC、建筑、事件、地点或其他来源引用。 |
| `type` | 委托、悬赏、探索或隐藏任务。 |
| `quality` | 普通、优秀、稀有、史诗或传说品质。 |
| `triggerCondition` | 任务从未触发进入可领取状态所需的条件。 |
| `acceptCondition` | 玩家领取任务时必须满足的条件。 |
| `objectives` | 任务需要完成的一个或多个同方向目标。 |
| `completionRule` | 多个目标之间的完成关系与最终完成条件。 |
| `rewardPoolId` | 任务完成后使用的奖励池标识。 |
| `validTurns` | 领取后可以保持进行中状态的有效回合数。 |
| `isUnique` | 是否属于当前对局中的唯一任务。 |

静态定义不保存当前状态、玩家标识、任务进度或剩余有效回合。这些内容均属于运行时任务实例。

单项任务不应为了实现特殊内容自行增加临时字段。确有公共需求时，应先判断该能力能否成为所有任务都可复用的标准字段、条件、目标或奖励类型，再统一扩展任务定义。

### 2.2 玩家任务实例

玩家成功领取任务后，系统根据静态定义创建独立的运行时任务实例。

任务实例建议包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `questInstanceId` | 当前对局中该任务实例的唯一标识。 |
| `questId` | 对应的任务静态定义标识。 |
| `ownerPlayerId` | 当前任务所属玩家。 |
| `status` | 进行中、已完成、待领取奖励、已放弃、已失效或已结束等状态。 |
| `objectiveProgress` | 各任务目标当前已经确认的进度。 |
| `remainingTurns` | 当前剩余有效回合数。 |
| `acceptedAtTurn` | 玩家成功领取任务的回合。 |
| `completedAtTurn` | 任务完成回合；尚未完成时为空。 |
| `endedAtTurn` | 任务最终结束回合；尚未结束时为空。 |
| `rewardState` | 奖励是否已经生成及发放的幂等状态。 |

任务实例只保存当前对局中的必要状态，不复制任务名称、描述、品质、完整目标与奖励池配置。需要展示或结算时，系统通过 `questId` 读取对应静态定义。

静态定义、运行时实例与执行逻辑保持分离，可以降低存档体积，并避免修改任务文案或平衡配置时产生多份不一致数据。

### 2.3 字段职责

任务目标与完成条件属于不同概念：

* `objectives` 描述玩家需要推进的具体目标及其进度口径。
* `completionRule` 描述一个或多个目标满足何种关系时任务完成。

例如，一个任务可以要求玩家收集 `3` 份铁矿；“收集铁矿”及目标数量属于任务目标，“该目标达到 `3 / 3` 时完成任务”属于完成规则。

发布者只描述任务来源，不直接承担生命周期管理。NPC、建筑或事件可以提供任务，但领取校验、任务栏占用、进度记录与奖励状态仍由任务系统统一管理。

## 3. 任务品质规范

任务品质采用游戏统一的五级品质体系：

| 品质 | 设计定位 |
| --- | --- |
| 普通 | 最基础且数量最多的任务，主要提供常见成长资源。 |
| 优秀 | 相比普通任务拥有更完整的流程或更丰富的奖励。 |
| 稀有 | 获取条件或完成难度较高，奖励价值明显提升。 |
| 史诗 | 较少出现，通常涉及高难度目标、稀有地点或重要剧情。 |
| 传说 | 极其稀有，仅用于少量具有显著价值的特殊任务。 |

任务品质主要用于描述任务的稀有程度、整体难度与预期奖励价值，不直接改变任务生命周期，也不自动决定任务目标类型。

高品质任务并不意味着必须包含更多目标。一个目标清晰但风险极高、机会稀少或具有重要剧情意义的任务，同样可以拥有较高品质。

任务品质不能绕过奖励平衡。传说任务可以提供更高价值或更独特的奖励，但仍不能直接授予游戏胜利、自动完成使命或无限生成永久成长资源。

当前任务系统不使用神话品质。神话品质仅作为游戏统一品质体系的未来扩展项保留，不进入当前任务池、任务随机权重与奖励平衡范围。

---

## 4. 任务目标规范

任务目标用于描述玩家需要完成的具体行为，是任务配置的核心部分。

当前任务目标可以包括但不限于：

| 目标方向 | 示例 |
| --- | --- |
| 收集 | 获得指定数量的材料、消耗品或其他合法物品。 |
| 交付 | 向指定 NPC、建筑或地点提交物品与资源。 |
| 击败 | 击败指定敌人、精英单位或首领。 |
| 探索 | 抵达区域、发现地点、揭示地图或调查场景。 |
| 交互 | 与指定 NPC、建筑、机关或场景完成交互。 |
| 制造 | 成功制造符合条件的装备、道具或其他物品。 |
| 事件 | 揭露、选择或完成符合条件的事件。 |

不同目标只读取对应业务系统已经确认的结果。例如：

* 击败目标由战斗系统确认。
* 获得与提交物品由背包与物品系统确认。
* 抵达和发现区域由地图系统确认。
* 制造成功由装备制造系统确认。
* 事件完成由事件系统确认。

任务系统不能通过客户端动画、玩家操作意图或尚未完成的过程提前增加进度。

每项任务应围绕一个核心目标方向设计。允许配置多个阶段或多个同方向目标，但不建议在普通任务中强行组合彼此无关的收集、战斗、探索与制造要求。

确需多个目标时，`completionRule` 必须明确采用全部满足、任意满足或指定顺序等统一规则，不能通过自然语言临时解释完成关系。

## 5. 奖励池规范

任务奖励统一通过奖励池（Reward Pool）配置。

任务静态定义只引用 `rewardPoolId`，具体奖励内容、数量与随机权重由奖励资源统一维护，避免同一奖励组合在多个任务中重复定义。

奖励内容包括但不限于：

* 元宝。
* 经验值。
* 手牌。
* 装备。
* 图纸。
* 材料。
* 药剂与消耗品。
* 基础属性点。
* 特殊道具。
* 地图情报。
* 特殊权限。
* 特殊剧情奖励。

一个任务可以配置一种或多种奖励。奖励池可以包含固定奖励与随机奖励，但必须明确两者的结算关系。

### 5.1 固定奖励

固定奖励在任务完成后必定生成，适合用于保证任务的基础收益。

例如：

```text
固定获得：5 个元宝
固定获得：10 点经验值
```

### 5.2 随机奖励

随机奖励从任务指定的奖励候选中按照权重抽取，用于增加任务收益的变化性。

随机奖励必须使用随机系统提供的任务随机流，不能直接调用系统随机函数，也不能受到未明确允许的公共随机因素影响。

奖励结果首次生成后必须立即记录。领取失败或重新连接时，只能继续发放已经生成的结果，不能重新抽取奖励。

### 5.3 奖励结算

任务奖励按照以下流程结算：

```text
确认任务已经完成
        │
        ▼
读取任务奖励池
        │
        ▼
生成并固定奖励结果
        │
        ▼
交由对应业务系统执行发放
        │
        ▼
记录奖励发放状态
        │
        ▼
任务结束
```

奖励发放应具备幂等性。同一任务实例的同一项奖励只能成功发放一次，断线重试、存档恢复或重复请求不能产生额外奖励。

涉及物品的奖励必须遵循背包与临时拾取规则；涉及元宝的奖励以元宝物品数量为单位；涉及永久成长的奖励必须遵循数值系统与等级系统规则。

## 6. 任务设计原则

### 6.1 目标明确

玩家应能够快速理解任务需要完成的主要目标。

任务名称、描述与目标文本应使用一致术语，并明确目标对象、所需数量、地点范围及其他必要条件。避免让玩家依赖猜测才能理解基础完成方式。

隐藏任务可以隐藏触发条件或部分剧情信息，但任务被正式领取后，仍应向玩家公开完成任务所必需的信息。

### 6.2 完成方式简单

每项任务应围绕一个核心目标方向进行设计，例如：

* 收集。
* 击败。
* 探索。
* 交付。
* 调查。

普通任务应尽量通过少量目标完成，避免连续嵌套过多阶段、递归生成任务或要求玩家同时维护多个互不相关的条件。

复杂剧情可以拆分为多个独立任务，通过明确的任务链逐步推进，而不是将全部剧情步骤塞入一个任务实例。

### 6.3 奖励与难度匹配

任务奖励应与任务品质、完成难度、预计流程长度、资源消耗与失败风险保持一致。

简单任务主要提供基础成长资源，高品质任务可以提供更高价值或更具特色的奖励。避免通过低成本、低风险且可重复的任务稳定获得高价值收益。

任务品质只提供奖励设计参考，最终奖励仍需结合具体目标和当前游戏阶段进行平衡。

### 6.4 鼓励探索

任务应尽可能引导玩家探索地图、交互 NPC 并体验不同区域的内容。

收集与战斗目标应具有合理的地点、敌人或剧情背景，避免大量任务仅通过反复击败同一目标或收集同一资源延长游戏时间。

任务目标应优先利用已有地图、事件、NPC、装备与经济内容，而不是为单项任务增加无法复用的特殊规则。

### 6.5 保持独立性

普通任务原则上应保持相互独立，使玩家能够根据任务栏空间与发展方向自由选择。

任务链属于允许的受控例外。任务依赖其他任务时，必须通过统一的前置任务条件进行配置，并遵循以下限制：

* 依赖关系必须明确且可以追踪。
* 不允许形成循环依赖。
* 任务链不应过长或长期占满玩家任务栏。
* 前置任务失效时，后续任务不能进入可领取状态。
* 唯一任务链必须保证关键内容仍具有明确归属。

### 6.6 配置优先

新增任务应优先通过已有条件、目标、完成规则与奖励池完成配置。

不得为单个任务在任务服务中增加 `if questId === ...` 等特殊判断。确有新机制需求时，应先设计通用目标或效果类型，并验证其能够被多个任务或其他系统复用。

### 6.7 职责分离

任务系统负责：

* 任务触发与领取校验。
* 任务栏数量限制。
* 目标匹配与进度记录。
* 生命周期状态迁移。
* 完成判断与奖励编排。
* 唯一任务状态管理。

任务系统不负责：

* 模拟战斗或判断伤害过程。
* 直接修改地图与世界状态。
* 绕过背包系统扣除或发放物品。
* 自行计算角色属性与等级成长。
* 直接完成使命或判断玩家胜利。

## 7. 高价值奖励规范

以下内容属于高价值任务奖励，应严格控制产出：

* 基础属性点。
* 高品质装备。
* 高品质图纸。
* 特殊权限。
* 特殊剧情奖励。
* 其他能够产生永久成长或稀缺世界变化的内容。

高价值奖励遵循以下规则：

* 原则上只出现在稀有、史诗或传说任务中。
* 必须与较高难度、较长流程、稀有触发条件或明确风险相匹配。
* 可重复任务不应稳定产出无限永久成长奖励。
* 基础属性点等永久成长奖励应设置严格的对局产出上限。
* 高品质装备与图纸仍需遵循装备品质、制造与背包规则。
* 特殊权限必须明确作用范围、持续时间及是否可以重复获得。

普通与优秀任务可以在特殊情况下提供少量高价值内容，但必须作为明确的低概率或一次性奖励进行平衡，不能成为常规投放方式。

## 8. 编号规范

任务定义统一使用项目资源 ID 规范，不将任务类型、名称或其他业务属性写入 ID。

统一格式如下：

```text
quest_<6位数字编号>
```

其中，`quest` 表示该资源属于任务系统，数字编号固定为六位十进制数字，范围为 `000001` 至 `999999`。

例如：

```text
quest_000001
quest_000002
quest_000003
quest_000004
```

每个任务 ID 必须唯一，并在创建后保持稳定。调整任务名称、类型、描述或奖励时，不应修改已有任务 ID；任务删除后，原编号也不得分配给其他任务。

任务 ID 只用于程序管理、配置引用、日志、存档与联机同步，不直接向玩家展示，也不参与任务品质、权重、完成条件或奖励计算。

如果未来确实需要向玩家展示简短任务编号，可以单独生成界面展示编号，但该编号不能代替稳定的 `questId`。

## 9. 命名规范

任务名称应简洁、明确，并能够体现主要任务内容或关键叙事对象。

例如：

* 收集遗失的矿石。
* 清剿森林狼群。
* 调查废弃神庙。
* 神秘商人的委托。

任务命名应遵循以下原则：

* 优先使用动词与目标对象，使玩家能够快速理解任务方向。
* 同一任务链保持统一的命名风格。
* 避免大量任务使用无法区分的通用名称。
* 避免名称直接泄露隐藏任务尚未公开的秘密结果。
* 避免使用与使命、事件或系统功能完全相同的名称造成误解。

任务名称属于玩家可见文本，可以根据项目本地化资源进行展示；任务 ID 始终使用稳定英文命名，不随显示语言变化。

## 10. 数据组织建议

任务定义、奖励池与运行逻辑应分别管理。

推荐资源结构如下：

```text
quests/
├── definitions/
│   ├── commission/
│   ├── bounty/
│   ├── explore/
│   └── hidden/
├── objectives/
├── reward-pools/
└── conditions/
```

程序负责：

* 加载并校验任务资源。
* 根据条件筛选可触发与可领取任务。
* 创建和维护玩家任务实例。
* 接收其他系统确认的业务结果。
* 推进目标并执行统一生命周期。
* 生成奖励并调用对应业务接口。

任务资源负责：

* 定义任务文本与类型。
* 引用标准条件和目标。
* 配置有效回合与唯一规则。
* 引用统一奖励池。

新增任务时，只需新增任务定义并引用已有目标、条件与奖励资源。新增一种公共目标或奖励能力时，应在对应定义与处理器注册表中统一扩展，而不是为单个任务创建专用服务。

---

## 11. 总体设计原则

任务系统始终遵循以下原则：

1. 使用统一的静态定义结构。
2. 静态配置与运行时任务实例相互分离。
3. 使用游戏统一的五级品质体系。
4. 任务目标简洁明确，并围绕一个核心方向设计。
5. 奖励价值与品质、难度、风险及流程长度相匹配。
6. 任务进度只接收其他系统已经确认的业务结果。
7. 奖励首次生成后保持稳定，重复请求不能重新抽取。
8. 普通任务保持独立，任务链使用统一前置条件配置。
9. 任务 ID 使用稳定命名空间，不依赖资源创建顺序。
10. 新增任务优先通过配置完成，不为单项任务增加特殊逻辑。

通过统一结构、目标体系、奖励池和命名规范，任务系统能够在保持底层流程稳定的同时持续扩充新的任务内容，并与地图、NPC、事件、战斗、经济及使命系统形成清晰且低耦合的联动关系。
