# 《开天辟地之大地的裂变》战斗结算

## 1. 系统定位

战斗结算用于汇总一次攻击、反击或其他战斗行为已经产生的最终结果，并将确定后的状态变化、后续通知、奖励资格及日志上下文交给对应系统。

战斗结算不负责重新执行：

* 攻击合法性计算。
* 闪避与暴击判定。
* 攻击值与伤害公式。
* 状态效果内部计算。
* 装备与技能效果计算。
* 奖励内容与掉落随机。

上述内容由战斗流程及对应业务系统完成。战斗结算只接收已经确认的过程结果，形成一次稳定、完整且不可重复消费的结算结果。

整体流程如下：

```text
战斗行为完成直接效果
        │
        ▼
收集攻击、响应、伤害与生命结果
        │
        ▼
校验结算数据完整性
        │
        ▼
确认并提交角色状态变化
        │
        ▼
生成统一战斗结算结果
        │
        ▼
按照顺序通知相关系统
        │
        ▼
输出前端摘要与统一日志上下文
        │
        ▼
关闭本次战斗上下文
```

本章中的“战斗结算”以单次战斗行为为单位，不代表进入或退出独立战斗场景。

---

## 2. 设计目标

战斗结算遵循以下设计目标：

### 2.1 单一结果

一次战斗行为只能生成一个最终结算结果。任务、使命、奖励和日志系统均消费同一结果，不能分别推测战斗发生了什么。

### 2.2 不可重复

结算结果需要拥有唯一标识。任何后续系统重复收到同一结算结果时，都不得再次推进进度、发放奖励或写入重复业务记录。

### 2.3 顺序稳定

角色状态提交、生命检查、后续触发、奖励资格和日志输出采用固定顺序，不能依赖对象遍历或客户端请求到达顺序。

### 2.4 职责分离

战斗结算描述“发生了什么”，其他系统根据自身规则决定“这个结果对我意味着什么”。

### 2.5 支持复盘

结算结果应包含足够的标识、数值摘要和状态变化，以支持前端展示、统一日志、问题定位及未来回放扩展。

---

## 3. 结算输入

战斗结算只能接收已经完成当前直接效果的合法战斗上下文。

建议输入包含：

| 数据 | 说明 |
| --- | --- |
| 战斗行为 ID | 当前攻击或战斗行为的唯一标识。 |
| 外层流程 ID | 发起本次行为的回合、事件、遭遇或效果标识。 |
| 结算顺序 | 当前对局中的权威递增顺序。 |
| 攻击方 | 发起当前行为的角色、NPC 或其他对象。 |
| 防守方 | 当前行为的主要目标。 |
| 攻击来源 | 普通攻击、技能、装备、手牌、状态或事件。 |
| 攻击方式 | 武器、技能或其他攻击定义标识。 |
| 伤害类型 | 物理、法术、真实或无伤害。 |
| 响应结果 | 防守方是否响应，以及响应产生的结果。 |
| 判定结果 | 闪避、暴击及其他随机判定结果。 |
| 数值摘要 | 攻击值、防御、穿透、伤害、护盾和生命变化。 |
| 状态变化 | 本次行为已经确认添加、刷新、叠层或移除的状态。 |
| 资源变化 | 本次行为已经支付或产生的合法资源变化。 |
| 生命状态变化 | 正常、击倒或死亡等生命状态转换。 |
| 特殊结果 | 反击、处决、位移或其他需要继续通知的结果。 |

结算输入不得只提供一句自然语言描述。所有需要被程序判断的结果必须使用结构化字段保存。

结算开始前，系统需要确认：

* 战斗行为 ID 尚未结算。
* 攻击方、防守方和攻击来源与原攻击上下文一致。
* 已经支付的行动与资源成本记录完整。
* 护盾、生命与状态变化符合对应系统输出。
* 生命状态转换与《06-生命、击倒与死亡》一致。
* 当前结算顺序晚于其依赖的所有直接效果。

输入不完整或彼此矛盾时，结算失败并记录错误，不得猜测缺失结果后继续发放奖励。

---

## 4. 战斗结果结构

### 4.1 主要结果

一次战斗行为可以形成以下主要结果：

| 结果 | 说明 |
| --- | --- |
| 请求无效 | 攻击未通过合法性检查，没有正式发起。 |
| 攻击失效 | 攻击正式发起后被主动防御或特殊规则完全取消。 |
| 攻击闪避 | 攻击有效，但目标自然闪避成功。 |
| 未被闪避但未造成伤害 | 攻击未被闪避，但因免疫或明确规则没有产生伤害。 |
| 未被闪避并造成伤害 | 攻击未被闪避并产生合法护盾或生命伤害。 |
| 目标进入击倒 | 当前行为使目标生命值降至 `0` 并进入击倒状态。 |
| 目标正式死亡 | 当前行为完成合法处决或其他正式死亡条件。 |
| 特殊完成 | 无伤害技能或特殊战斗行为按照自身条件完成。 |

“攻击成功”不能作为唯一结果字段，因为成功可能表示未被闪避、造成伤害、施加状态或只是完成无伤害效果。结算结果应保留明确的分阶段信息。

### 4.2 结果标记

除主要结果外，结算可以记录多个独立标记，例如：

* 是否正式发起。
* 是否使用主动防御。
* 是否被完全防御。
* 是否闪避。
* 是否暴击。
* 是否造成护盾伤害。
* 是否造成生命伤害。
* 是否施加状态。
* 是否触发反击或追加效果。
* 是否使目标进入击倒。
* 是否确认目标正式死亡。
* 是否满足目标自身的击败条件。

这些标记可以同时成立。例如，一次攻击可以同时“未被闪避”“暴击”“造成护盾伤害”“造成生命伤害”并“使目标进入击倒”。

### 4.3 数值摘要

数值摘要建议包含：

```text
攻击值
有效防御
基础伤害
暴击结算后伤害
最终伤害
护盾吸收值
生命伤害值
过量伤害值
结算前后护盾
结算前后生命值
```

未参与当前行为的数值使用 `null` 或省略对应可选字段，不能使用具有业务含义的 `0` 冒充“不适用”。

例如，攻击被闪避时没有基础伤害计算结果，应将伤害计算摘要标记为不适用，而不是伪造“未被闪避但最终伤害为 `0` 的攻击”。

## 5. 角色状态提交

### 5.1 提交原则

战斗过程中产生的行动、资源、护盾、生命与状态变化，需要作为当前战斗行为的一组有序变化提交。

提交时应保证：

* 每项变化只应用一次。
* 变化顺序与战斗流程一致。
* 任意资源都不突破合法边界。
* 已由技能系统支付的成本不在结算阶段重复扣除。
* 已由状态系统完成的状态变化不在结算阶段重新计算。
* 失败时不会留下只应用一半的角色状态。

战斗结算不重新调用随机系统，也不重新进行伤害计算。它只校验并提交前序阶段已经确认的结果。

### 5.2 生命状态

生命相关变化按照以下顺序确认：

```text
提交护盾变化
        │
        ▼
提交当前生命值变化
        │
        ▼
检查生命值边界
        │
        ▼
确认正常、击倒或死亡状态
```

目标进入击倒与目标正式死亡是两个不同结果。

进入击倒只表示目标开始等待救援，不应立即触发正式死亡、轮回或击杀奖励。只有《06-生命、击倒与死亡》确认正式死亡，或目标规则明确确认已被击败后，才能产生对应后续通知。

### 5.3 状态效果

技能、装备或攻击附加的 Buff／Debuff 由状态系统完成施加、刷新、叠层或移除。

战斗结算只记录：

* 状态定义 ID。
* 状态实例 ID。
* 目标 ID。
* 施加结果。
* 变化前后层数。
* 变化前后剩余回合。

状态属性修正由数值系统在状态变化后重新聚合。战斗结算不能直接覆盖角色最终属性。

### 5.4 资源与消耗

战斗行为可能消耗：

* 主要行动与移动力。
* 当前灵力或其他职业资源。
* 物品与元宝。
* 手牌。
* 技能次数或冷却。
* 状态层数。

这些消耗通常在技能、手牌或攻击正式发起时已经支付。结算阶段负责确认最终状态和记录来源，不因攻击被防御、闪避或未造成伤害而自动返还。

确实需要返还的能力必须由自身规则生成明确的资源恢复效果，不能由战斗结算根据失败结果自行推断。

## 6. 后续通知

### 6.1 通知定位

战斗结算完成角色状态提交后，生成结构化战斗结果通知。

通知描述已经发生的事实，例如：

```text
攻击正式发起
攻击被闪避
攻击未被闪避
造成护盾伤害
造成生命伤害
目标进入击倒
目标正式死亡
目标被确认击败
```

通知本身不直接修改任务、使命、经济或背包状态。各系统订阅自己关心的结果，并按照自身规则处理。

### 6.2 通知顺序

建议按照以下顺序发布后续通知：

1. 攻击行为完成。
2. 主动防御与闪避结果确认。
3. 伤害及资源变化确认。
4. 状态添加、刷新、叠层与移除确认。
5. 击倒或正式死亡结果确认。
6. 目标击败资格确认。
7. 任务、使命与特殊事件检查。
8. 奖励资格与掉落请求。
9. 胜利条件检查。
10. 前端摘要与统一日志输出。

同一结算结果的通知顺序必须稳定，并携带相同的战斗结算 ID。

### 6.3 触发循环限制

后续通知可以触发反击、状态或特殊事件，但必须具有明确的来源链和触发次数。

新触发的攻击需要建立新的战斗行为 ID 和攻击上下文，不能继续修改已经完成的原结算结果。

任何通知处理器都不得再次消费同一结算结果以产生相同奖励或进度，避免无限循环与重复结算。

---

## 7. 战斗奖励

### 7.1 奖励资格

战斗结算只负责提供奖励资格所需的事实，不直接决定具体奖励内容。

常见奖励资格包括：

* 击败普通敌对 NPC。
* 击败精英单位。
* 击败 Boss。
* 完成悬赏目标。
* 完成特殊事件中的战斗条件。

目标进入击倒不等于目标已经被击败。奖励只能在目标所属系统确认死亡或满足自身击败条件后生成。

玩家之间的战斗默认不产生固定经验、元宝或掉落奖励。特殊模式、任务或事件需要提供奖励时，必须使用明确配置，不能复用普通 NPC 击败奖励。

### 7.2 奖励来源

奖励内容由目标、事件、任务或场景配置提供，可以包括：

* 经验值。
* 元宝。
* 材料。
* 消耗品。
* 装备。
* 图纸。
* 手牌。
* 任务或使命进度。
* 特殊事件入口。

战斗结算不能在代码中按照敌人名称写死奖励。

### 7.3 奖励生成流程

奖励按照以下流程生成：

```text
结算确认目标被击败
        │
        ▼
读取目标或场景奖励配置
        │
        ▼
确定合法奖励接收者
        │
        ▼
调用掉落随机流生成随机奖励
        │
        ▼
生成奖励结果
        │
        ▼
交给经验、背包、手牌等系统处理
        │
        ▼
记录实际发放与未能接收的内容
```

随机奖励必须调用随机系统中的掉落随机流，不能由战斗结算直接使用系统随机函数。

### 7.4 奖励接收

不同奖励由对应系统处理：

| 奖励 | 负责系统 |
| --- | --- |
| 经验值 | 等级与经验系统。 |
| 元宝 | 背包与经济系统，按照元宝物品数量处理。 |
| 材料、消耗品、装备、图纸 | 背包与物品系统。 |
| 手牌 | 手牌系统，从共享牌库按照合法方式获得。 |
| 任务进度 | 任务系统。 |
| 使命进度 | 使命系统。 |

元宝与其他物品均需要遵循统一拾取流程。背包无法容纳奖励时，按照临时拾取区、地图掉落或奖励来源自身规则处理，不能绕过背包空间直接增加隐藏余额。

### 7.5 奖励归属

V1 默认由完成目标最后一个有效击败条件的角色获得个人击败奖励。

团队奖励、协助奖励、伤害占比及共享掉落不在 V1 基础范围。任务、事件或目标配置明确指定所有参与者获得奖励时，按照对应配置执行。

奖励归属只根据权威战斗结果和目标规则判断，不能依赖客户端自行报告“最后一击”。

## 8. 任务、使命与特殊事件

### 8.1 任务进度

战斗结算可以向任务系统提交：

* 攻击指定目标。
* 对指定目标造成生命伤害。
* 为指定目标施加状态。
* 使指定目标进入击倒。
* 救援击倒角色。
* 击败指定目标。

任务系统根据任务目标决定是否推进。战斗结算不能直接修改任务进度字段。

### 8.2 使命进度

使命系统只消费与当前使命相关的已确认结果，例如首次击败 Boss、完成指定战斗挑战或救援其他玩家。

使命属于隐藏胜利条件。战斗结算通知不得向其他玩家泄露使命内容或是否因此推进了隐藏使命。

### 8.3 特殊事件与剧情

击败特殊 NPC、Boss 或世界目标后，可以向事件系统提交后续触发事实。

```text
目标被确认击败
        │
        ▼
战斗结算发布结果
        │
        ▼
事件系统检查触发条件
        │
        ▼
生成事件、剧情或世界变化
```

战斗结算只负责发布结果，不能直接打开副本、修改天气、改变地图或推进剧情阶段。

## 9. 结果记录与统一日志

### 9.1 结构化结果

每次正式发起的战斗行为都应生成结构化结算结果，用于：

* 前端战斗过程展示。
* 后续系统消费。
* 调试与异常定位。
* 存档一致性检查。
* 未来回放扩展。

建议至少记录：

```text
结算 ID
权威顺序
攻击方与防守方
攻击来源与攻击方式
主动防御结果
闪避与暴击结果
伤害类型与数值摘要
护盾与生命变化
状态变化
击倒、死亡或击败结果
后续通知摘要
奖励处理摘要
```

结构化战斗结果属于游戏业务数据，不等于磁盘日志文件。

### 9.2 日志系统交接

战斗结算完成后，通过项目统一日志工具输出必要日志。

日志功能统一使用：

```text
Battle
```

日志模块填写实际输出日志的类名，例如：

```text
BattleSettlementService
```

日志内容使用英文完整句子，并遵循《15-日志系统/01-日志文档规范》与《15-日志系统/02-日志保存机制》。禁止建立独立于统一日志系统之外的“战斗日志文件”。

示例：

```text
[2026-08-08 12:30:15.021][INFO ][PlayerA][Battle ][BattleSettlementService] PlayerB took 18 physical health damage and entered the downed state.
```

详细计算步骤可以使用 `DEBUG` 或 `TRACE`；最终攻击结果、击倒、死亡与奖励使用 `INFO`；异常或不一致使用 `WARN` 或 `ERROR`。

日志写入失败不得回滚已经完成的战斗结算，也不得再次通过日志系统记录同一日志异常。

### 9.3 前端展示

前端根据结构化结算结果生成玩家可读的战斗摘要，例如：

```text
玩家 A 使用长剑攻击玩家 B。
玩家 B 未使用主动防御。
自然闪避失败。
本次攻击造成 23 点物理伤害。
护盾吸收 5 点伤害。
生命值降低 18 点。
玩家 B 进入击倒状态。
```

前端展示不能重新计算伤害，也不能根据动画播放结果决定暴击、闪避、奖励或生命状态。

## 10. 幂等与异常处理

### 10.1 幂等规则

每个战斗行为 ID 只能成功结算一次。

后续系统消费结算结果时，使用战斗结算 ID 和通知类型组成稳定的消费标识，例如：

```text
battle-settlement.000128:quest-progress
battle-settlement.000128:reward-generation
battle-settlement.000128:mission-check
```

重复请求应返回已经存在的结果或明确拒绝，不得再次应用状态、发放奖励或推进进度。

### 10.2 结算异常

发生以下情况时，结算应视为异常：

* 战斗上下文缺少必要字段。
* 结算结果与角色当前状态不一致。
* 同一行为被提交不同的最终结果。
* 生命值、护盾或资源越界。
* 后续通知缺少稳定结算 ID。
* 奖励请求无法确定合法来源或接收者。

结算异常不得通过猜测修复。系统应保留原有合法状态、输出错误日志，并将当前战斗行为标记为需要检查。

后续通知或日志单独失败时，不应撤销已经成功提交的角色生命与资源状态；系统应记录待重试或失败结果，并依靠幂等标识防止重复消费。

---

## 11. 特殊结算

部分战斗结果可以触发额外逻辑，例如：

* 击败 Boss。
* 完成悬赏任务目标。
* 触发隐藏事件。
* 达成使命条件。
* 推进世界剧情。
* 激活特殊装备或契约。

特殊逻辑仍然需要通过标准通知接口执行。

例如：

```text
玩家击败特殊 NPC
        │
        ▼
完成战斗结算并生成唯一结果
        │
        ▼
通知任务系统
        │
        ▼
任务系统独立判断目标是否完成
```

特殊结果不能在战斗结算主流程中按照 NPC、技能或任务 ID 增加硬编码分支。

## 12. V1 设计范围

V1 阶段支持：

* 单次战斗行为的结构化结算结果。
* 主动防御、闪避、暴击与伤害结果记录。
* 护盾、生命、击倒与正式死亡结果提交。
* 状态与资源变化摘要。
* 稳定的后续通知顺序。
* 任务、使命、事件与胜利条件通知。
* 基础奖励资格与奖励生成接口。
* 经验、元宝、物品和手牌奖励交接。
* 统一日志系统交接。
* 结算与奖励消费幂等保护。

以下内容保留至战斗系统 `V2` 目录：

* 完整战斗录像。
* 可交互战斗回放。
* 复杂排行榜。
* PvP 积分系统。
* 仇恨与威胁统计。
* 伤害占比与协助奖励。
* 复杂战斗数据分析。

## 13. 设计原则

战斗结算遵循以下设计原则：

事实输出原则

战斗结算只输出已经确认的事实，不重新计算攻击、伤害、状态或装备效果。

单一结果原则

任务、使命、奖励、前端与日志系统消费同一份结构化结算结果，不能分别推断战斗过程。

状态先行原则

先完成角色状态提交和生命检查，再通知任务、奖励、事件与胜利条件系统。

击倒分离原则

目标进入击倒不等于目标已经死亡或被击败，不得提前发放击杀奖励。

幂等消费原则

结算、进度、奖励与日志上下文均使用稳定标识，避免重复应用与重复发放。

职责分离原则

战斗结算提供结果和资格，具体奖励、任务、使命、物品与经济变化由对应系统负责。

日志统一原则

战斗结果通过项目统一日志工具输出，不建立独立战斗日志文件或另一套日志格式。

配置优先原则

奖励、特殊触发和目标击败规则来自配置与通用处理器，不在结算主流程中编写内容专属分支。

---

## 14. 小结

战斗结算将单次攻击或其他战斗行为已经确认的响应、判定、伤害、状态与生命结果汇总为唯一结构化记录，并按照稳定顺序通知任务、使命、事件、奖励、前端与日志系统。

结算不会重新计算战斗过程，也不会把击倒误判为正式击败。通过状态先行、结果唯一、幂等消费和职责分离，战斗系统能够可靠地连接角色成长、经济、背包、任务、使命及世界变化，同时为调试和未来回放提供统一的数据基础。
