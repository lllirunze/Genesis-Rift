# 《开天辟地之大地的裂变》日志保存机制

## 1. 设计目的

日志保存机制（Log Storage Specification）用于统一管理项目运行过程中产生的日志文件，为开发调试、运行记录查询、游戏过程复盘及异常问题定位提供稳定的保存基础。

日志保存机制应满足以下目标：

* 所有日志统一保存，便于集中管理；
* 日志文件按照创建时间自动命名；
* 单个日志文件容量受控，避免无限增长；
* 日志文件达到指定大小后自动切换；
* 多个模块同时产生日志时保持稳定顺序；
* 日志写入失败不得改变正常游戏结果；
* 日志文件采用统一编码，保证跨平台兼容性；
* 日志文件能够与本局游戏和对应存档建立关联。

日志文件主要服务于人工阅读、问题排查和过程复盘，不属于游戏存档，也不能仅凭日志文件恢复完整游戏状态。

---

## 2. 日志目录

服务端及本地开发环境产生的日志文件，统一保存在项目运行目录下的 `logs/` 文件夹中。

目录结构如下：

```text
logs/
├── latest.log
├── game_20260801_123015_021.log
├── game_20260801_125233_417.log
├── game_20260801_131508_006.log
└── game_20260802_091522_315.log
```

各类文件职责如下：

| 文件 | 说明 |
| --- | --- |
| `latest.log` | 当前程序正在写入的活动日志文件，便于开发人员快速查看最新日志。 |
| `game_*.log` | 已经关闭并完成归档的历史日志文件，按照活动文件创建时间命名。 |

如果 `logs/` 文件夹不存在，日志系统应在初始化时自动创建。

浏览器客户端不能直接向项目根目录写入文件。客户端日志默认通过统一接口提交至权威服务端；在纯前端开发环境中，可暂时输出至浏览器开发工具，但不得伪装成已经持久化的服务端日志。

---

## 3. 日志文件格式

### 3.1 文件类型

日志文件统一采用：

```text
.log
```

`.log` 文件本质上属于纯文本文件，可以直接使用 VS Code、Notepad++、记事本及其他文本编辑器打开。

每条日志的文本格式统一遵循《01-日志文档规范》，保存机制不得自行改变字段顺序或格式。

---

### 3.2 字符编码

所有日志统一采用：

```text
UTF-8
```

日志内容统一使用英文输出，保证不同平台之间具有一致的检索与分析结果。

文件大小必须按照 UTF-8 编码后的实际字节数计算，不能使用 JavaScript 字符串长度代替实际字节数。

---

### 3.3 换行符

每条日志独占一行。

日志工具应统一处理换行符，不允许业务模块主动在日志内容中插入换行。无论运行平台采用何种换行方式，读取日志时都应能够按照单条日志进行正确分割。

异常堆栈等多行信息应转换为安全的单行表示，或通过结构化附加数据单独保存，不能破坏“一条日志对应一行”的基本规则。

---

## 4. 日志文件命名

### 4.1 命名格式

历史日志文件统一采用以下格式：

```text
game_yyyyMMdd_HHmmss_SSS.log
```

例如：

```text
game_20260801_123015_021.log
```

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| `game` | 固定文件前缀 | `game` |
| `yyyy` | 四位年份 | `2026` |
| `MM` | 两位月份 | `08` |
| `dd` | 两位日期 | `01` |
| `HH` | 两位小时，采用 24 小时制 | `12` |
| `mm` | 两位分钟 | `30` |
| `ss` | 两位秒 | `15` |
| `SSS` | 三位毫秒 | `021` |
| `.log` | 文件扩展名 | `.log` |

文件名中的时间表示该活动日志文件的创建时间，而不是关闭时间或最后一条日志的产生时间。

---

### 4.2 活动文件创建规则

日志系统初始化时，应立即创建新的 `latest.log` 活动文件，并记录该文件的创建时间。

例如：

```text
程序启动时间：2026-08-01 12:30:15.021
活动文件：latest.log
预定归档名称：game_20260801_123015_021.log
```

程序运行期间，所有日志默认写入 `latest.log`。当程序正常关闭或日志文件达到容量限制时，再将该活动文件归档为预定的时间戳名称。

该设计能够避免依赖符号链接、硬链接或同时写入两个文件，保证 Windows、macOS 和 Linux 环境下的行为一致。

如果程序启动时发现上一次运行遗留的非空 `latest.log`，应先将其安全归档，再创建新的活动文件，避免覆盖尚未保存的日志。

---

### 4.3 文件名冲突

日志文件名精确到毫秒，正常情况下不会发生冲突。

如果目标归档文件已经存在，日志系统不得覆盖原文件，也不得使用 `_002`、`_003` 等顺序编号。系统应重新获取一个晚于原创建时间的可用时间值，再生成新的合法文件名。

多进程同时运行时，每个权威游戏服务进程应使用独立的运行目录或日志目录，避免多个进程共同维护同一个 `latest.log`。

---

## 5. 日志文件大小限制

为了避免单个日志文件过大并影响读取速度与管理效率，统一规定：

```text
单个日志文件最大容量：50 MB
```

换算为字节：

```text
50 × 1024 × 1024 = 52,428,800 Bytes
```

日志系统在写入每条日志前，应按照 UTF-8 编码后的实际字节数判断：

```text
当前文件大小 + 本次日志大小 + 换行符大小
```

若写入后将超过 `50 MB`，则应先切换日志文件，再将本条日志完整写入新的活动文件。

单条日志不得被拆分到两个文件中。日志工具还应限制异常大的单条日志内容，避免一次错误信息绕过文件容量管理规则。

`50 MB` 属于日志文件切换阈值，不代表整个 `logs/` 目录的总容量限制。历史日志的保留与清理由运行环境统一管理，初始版本不主动删除历史日志。

---

## 6. 日志文件切换

当活动日志文件达到大小限制时，应自动执行以下流程：

```text
暂停接收新的文件写入任务
        │
        ▼
完成队列中已经排在切换前的日志
        │
        ▼
刷新并关闭 latest.log
        │
        ▼
按照创建时间归档当前文件
        │
        ▼
创建新的 latest.log
        │
        ▼
恢复后续日志写入
```

例如：

```text
latest.log
    │
    ├── 归档为 game_20260801_123015_021.log
    │
    ▼
创建新的 latest.log
    │
    ├── 再次达到 50 MB
    │
    ▼
归档为 game_20260801_125233_417.log
```

新的活动文件始终记录独立的创建时间，并在下一次切换或关闭时使用该时间生成归档名称。

日志文件切换必须作为写入队列中的原子操作执行。切换期间产生的新日志可以暂存在队列中，但不能写入已经关闭的文件，也不能绕过队列直接写入新文件。

---

## 7. `latest.log`

为了方便开发调试，日志系统维护一个固定入口：

```text
latest.log
```

`latest.log` 始终表示当前程序正在写入的活动日志文件。

例如：

```text
logs/
├── latest.log
├── game_20260801_123015_021.log
└── game_20260801_125233_417.log
```

开发人员无需根据时间寻找当前文件，只需打开 `latest.log` 即可查看当前运行日志。

发生日志切换时，旧的 `latest.log` 被原子归档，随后立即创建新的 `latest.log`。`latest.log` 不是历史文件的副本，也不与时间戳文件进行双写。

程序正常关闭时，应刷新并关闭 `latest.log`，再将其归档为对应时间戳文件。若活动文件为空，可以直接删除或不生成历史归档。

---

## 8. 日志写入规范

### 8.1 追加写入

日志采用追加方式写入，每条日志独占一行。

例如：

```text
[2026-08-01 12:30:15.021][INFO ][Runze  ][Battle ][BattleService] Player attacked Goblin and dealt 25 damage.
[2026-08-01 12:30:16.512][INFO ][Runze  ][Move   ][MoveController] Player entered tile (3,-1,-2).
[2026-08-01 12:30:18.107][DEBUG][-------][Random ][RandomService] Generated random value 87.
```

日志系统应保证：

* 日志按照进入统一队列的顺序写入；
* 每条日志完整写入；
* 不覆盖已有日志内容；
* 单条日志不得跨文件保存；
* 所有业务日志均通过统一日志工具写入；
* 写入完成前不得复用或修改对应日志记录对象。

---

### 8.2 游戏局标识

每次游戏开始时，应生成稳定的游戏局 ID（Game Session ID）。日志系统应在游戏开始、存档、读档和游戏结束等关键日志中记录该 ID。

游戏局 ID 用于：

* 区分同一程序运行期间的不同游戏；
* 关联分散在多个文件中的日志；
* 将日志与对应存档建立联系；
* 过滤其他调试或系统生命周期日志。

游戏局 ID 不替代日志时间和玩家 ID，也不应包含玩家隐藏信息。

---

### 8.3 日志顺序

统一日志工具应在日志进入写入队列时，为其分配单调递增的内部序列号。

序列号用于确定同一权威进程内日志的严格先后顺序，避免多个事件在同一毫秒发生时仅依赖时间字段排序。

可读日志文件仍保持《01-日志文档规范》规定的格式。序列号可以作为日志记录的内部元数据，用于后续结构化日志、问题定位或精确复盘扩展。

初始版本中的文本日志主要支持人工复盘。若未来需要通过日志自动重放并恢复游戏状态，应另行设计完整的领域事件记录，不得直接把普通调试日志当作存档使用。

---

## 9. 并发写入

由于多个模块可能在同一时间产生日志，日志系统必须统一管理异步写入。

需要保证：

* 同一活动文件始终只有一个统一写入者；
* 不同日志不会发生内容交叉；
* 文件切换过程中不会主动丢弃已经入队的日志；
* 日志按照进入队列的顺序写入；
* 业务模块不直接持有或操作文件句柄。

项目采用统一异步日志队列进行管理。

整体流程如下：

```text
业务模块产生日志
        │
        ▼
统一日志工具完成格式化
        │
        ▼
分配内部序列号
        │
        ▼
进入日志写入队列
        │
        ▼
单一写入者顺序写入文件
```

Node.js 环境不应依赖业务代码自行添加线程锁。即使文件写入采用异步方式，也必须由同一日志管理器串行提交，防止多个未受控的异步写入同时操作活动文件。

日志队列应设置合理的容量与降级策略，避免磁盘异常或写入速度过慢时无限占用内存。

---

## 10. 异常处理

日志保存发生异常时，不应改变已经确定的游戏业务结果，也不应导致正常游戏流程直接崩溃。

### 10.1 日志目录创建失败

日志工具内部通过标准错误输出：

```text
Failed to create log directory.
```

---

### 10.2 日志文件创建失败

日志工具内部通过标准错误输出：

```text
Failed to create log file.
```

---

### 10.3 日志写入失败

日志工具内部通过标准错误输出：

```text
Failed to write log message.
```

该错误不得再次通过日志系统记录，避免形成无限递归。

---

### 10.4 日志文件切换失败

日志文件切换失败后，应停止继续使用状态不明确的文件句柄，并通过标准错误输出失败信息。

尚未写入的日志可以按照队列降级策略暂存或丢弃，但不能阻塞游戏主流程。恢复写入后，应记录日志系统曾发生中断的事实。

---

### 10.5 降级边界

`console.error()` 等标准错误输出只能由日志工具内部作为最后降级手段使用。业务模块仍然禁止绕过日志工具直接输出正式日志。

日志系统不得因为自身异常重复重试至无限循环，也不得在内存中无限积压待写日志。

---

## 11. Git 管理

日志文件属于运行时数据，不得提交至 Git 仓库。

项目根目录的 `.gitignore` 应包含：

```gitignore
logs/
```

文档、日志配置和日志系统代码应正常进入版本控制，实际生成的 `.log` 文件及 `logs/` 目录内容不进入版本控制。

---

## 12. 配置参数

日志配置应集中管理，不允许不同模块分别定义文件大小、编码或命名规则。

概念配置如下：

```ts
const logConfig = {
  directory: "logs",
  latestFile: "latest.log",
  filePrefix: "game",
  fileExtension: ".log",
  fileNamePattern: "yyyyMMdd_HHmmss_SSS",
  maxFileSizeBytes: 50 * 1024 * 1024,
  encoding: "utf-8",
} as const;
```

配置字段遵循以下规则：

* 文件大小统一使用字节；
* 文件大小按照 UTF-8 编码后的实际字节数判断；
* 路径由日志工具统一解析，业务模块不拼接绝对路径；
* 默认配置应满足本规范，环境配置只能在允许范围内覆盖；
* 生产环境不得通过配置关闭 `WARN` 和 `ERROR` 日志；
* 日志配置错误时，应回退至安全默认值或关闭文件写入，不能影响游戏启动。

---

## 13. 最终规范

整个项目统一遵循以下规则：

1. 所有服务端日志统一保存在 `logs/` 文件夹中。
2. 日志文件统一采用 `.log` 扩展名。
3. 日志文件统一使用 UTF-8 编码。
4. 历史文件命名格式为 `game_yyyyMMdd_HHmmss_SSS.log`。
5. 文件名精确到毫秒，并表示活动文件创建时间。
6. 程序每次启动时自动创建新的 `latest.log`。
7. 单个日志文件的切换阈值为 `50 MB`。
8. 写入前必须按照 UTF-8 实际字节数判断是否需要切换。
9. 超过容量后自动归档当前文件，并创建新的 `latest.log`。
10. 不使用 `_002`、`_003` 等顺序编号。
11. 单条日志不得拆分至多个文件。
12. 所有日志采用追加方式写入，并且每条日志独占一行。
13. `latest.log` 始终表示当前活动日志文件。
14. 所有文件写入统一经过异步队列和单一写入者。
15. 日志保存异常不得改变正常游戏业务结果。
16. 实际生成的 `logs/` 目录不得提交至 Git 仓库。
17. 文本日志用于调试和人工复盘，不能代替游戏存档。
18. 浏览器客户端不得绕过服务端直接伪造权威业务日志。

最终目录如下：

```text
logs/
├── latest.log
├── game_20260801_123015_021.log
├── game_20260801_125233_417.log
├── game_20260801_131508_006.log
└── game_20260802_091522_315.log
```

通过统一目录、活动文件、时间归档、容量切换与异步写入队列，可以在不影响正常游戏流程的前提下，为开发调试、运行分析和游戏复盘提供稳定、清晰且可维护的日志保存基础。
