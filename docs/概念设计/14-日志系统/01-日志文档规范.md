# 《开天辟地之大地的裂变》日志文档规范

## 1. 设计目的

日志系统（Logging System）用于统一整个项目的日志输出格式，为开发调试、问题定位、游戏复盘及后期维护提供稳定的信息基础。

所有需要输出正式日志的模块均应通过统一日志工具完成，不允许在业务代码中直接使用 `console.log()`、`console.error()`、`System.out.println()` 或其他临时打印方式记录正式日志。纯规则函数只返回业务结果，不直接执行日志文件写入；服务端编排层负责在结果确认后完成记录。

统一的日志规范主要承担以下目标：

* 提高日志的可读性；
* 快速定位异常来源；
* 支持开发阶段调试；
* 为游戏复盘提供完整依据；
* 便于后期日志分析与统计；
* 保持整个项目统一的代码风格。

日志只负责记录已经发生的事实，不负责决定游戏结果，也不能代替具体业务系统保存运行时状态。

---

## 2. 日志格式

所有可读日志均采用以下统一格式：

```text
[2026-08-01 12:30:15.021][INFO ][Runze  ][Battle ][BattleService] Player attacked Goblin and dealt 25 damage.
```

整体结构如下：

```text
[时间][日志等级][日志对象][日志功能][日志模块] 日志内容
```

格式遵循以下规则：

* 所有字段均使用半角中括号包裹；
* 日志内容与最后一个 `]` 之间保留一个半角空格；
* 除日志模块外，其余字段均采用固定宽度；
* 固定宽度字段统一左对齐，并在右侧补充空格；
* 字段顺序保持固定，不允许业务模块自行调整；
* 日志工具负责完成时间、缩写、补位和最终格式化，业务模块不得自行拼接完整日志文本。

本格式主要用于开发人员阅读、调试和复盘。日志的写入顺序、文件切换、存档关联及保存边界，将在《02-日志保存机制》中统一规定。

---

## 3. 字段规范

### 3.1 时间（Time）

时间格式统一为：

```text
yyyy-MM-dd HH:mm:ss.SSS
```

例如：

```text
[2026-08-01 12:30:15.021]
```

时间字段遵循以下规则：

* 使用生成该日志的权威进程本地时间；
* 精确到毫秒；
* 所有日志必须记录时间；
* 同一局游戏的权威业务日志应由同一服务端时钟生成；
* 时间只用于展示与检索，不能单独作为游戏事件的唯一顺序依据。

游戏事件的严格先后顺序应由日志保存机制中的序列号统一确定，避免设备时间偏差影响复盘结果。

---

### 3.2 日志等级（Level）

日志等级统一使用英文大写，固定宽度为 `5` 个字符，并采用左对齐方式输出。

例如：

```text
[TRACE]
[DEBUG]
[INFO ]
[WARN ]
[ERROR]
```

| 等级 | 说明 |
| --- | --- |
| `TRACE` | 最详细的运行过程日志，仅在开发调试或专项排查时开启。 |
| `DEBUG` | 开发调试日志，用于记录算法输入、筛选过程及中间结果。 |
| `INFO` | 正常业务日志，用于记录已经完成的重要游戏行为。 |
| `WARN` | 警告日志，表示出现异常情况，但程序仍可按照规则继续运行。 |
| `ERROR` | 错误日志，表示某项功能执行失败、状态校验失败或发生异常。 |

日志等级应根据事件影响选择，不得为了方便检索而将所有日志统一记录为 `INFO` 或 `ERROR`。

---

### 3.3 日志对象（Target）

日志对象表示本条日志主要涉及的玩家。

该字段固定宽度为 `7` 个字符，统一采用左对齐、右侧补空格的方式输出。

#### 玩家名称长度小于或等于 7

保持玩家名称原样输出，不足部分在右侧补充空格。

例如：

```text
[Tom    ]
[Runze  ]
[Alice  ]
[Player1]
```

#### 玩家名称长度大于 7

为了保证日志宽度一致，采用以下缩写形式：

```text
前三个字符 + "*" + 后三个字符
```

例如：

```text
[Run*ple]
[Pla*001]
[Ale*ice]
```

缩写规则如下：

* 保留名称的前三个字符；
* 使用 `*` 表示中间内容被省略；
* 保留名称的最后三个字符；
* 最终输出宽度固定为 `7` 个字符。

日志对象只用于提高可读性，不能作为玩家的唯一身份标识。日志内部仍应保存稳定的玩家 ID，以支持重名玩家区分与准确复盘。

#### 与玩家无关

若日志与任何玩家无关，则统一输出：

```text
[-------]
```

常见情况包括：

* 天气变化；
* NPC 刷新；
* 地图生成；
* 游戏启动；
* 游戏关闭；
* 自动存档。

---

### 3.4 日志功能（Action）

日志功能用于表示当前日志所属的业务类别，便于后续筛选、分类和统计。

日志功能遵循以下规则：

* 使用一个英文单词；
* 使用 PascalCase；
* 固定宽度为 `8` 个字符；
* 统一左对齐，并在右侧补充空格；
* 只表示所属业务，不描述具体发生的事件；
* 所有可用值由日志系统集中维护，业务模块不得随意新增。

例如：

```text
[Battle ]
[Move   ]
[Map    ]
[Level  ]
[Item   ]
[Equip  ]
[Shop   ]
[Quest  ]
[Weather]
[Random ]
[Save   ]
[Load   ]
[Npc    ]
[Hand   ]
[Player ]
[System ]
```

真正发生的事件由日志内容及对应结构化数据共同描述。

---

### 3.5 日志模块（Module）

日志模块表示日志的直接代码来源。

该字段不限制宽度，应填写稳定且能够定位源码的来源名称。

对于面向对象模块，优先填写输出日志的类名，例如：

```text
[BattleService]
[InventoryService]
[MoveController]
[WeatherManager]
[MissionGenerator]
[RandomService]
```

对于当前 TypeScript 项目中的函数式模块，应填写稳定的模块名称或服务名称，不应填写匿名函数名、临时变量名或可能随构建变化的内容。

日志模块名称应能够帮助开发人员快速定位代码，但不能包含本地绝对路径、设备用户名或其他仅在单台设备上有效的信息。

---

### 3.6 日志内容（Message）

日志内容统一采用英文描述。

日志内容遵循以下规则：

* 使用完整句子；
* 准确描述已经发生的事件或失败原因；
* 与最后一个 `]` 之间保留一个半角空格；
* 保持简洁、明确，避免无意义的重复信息；
* 不使用中文，保证跨平台检索与分析的一致性；
* 不记录密码、完整随机种子、隐藏使命、神鬼契约等不应公开的敏感信息。

例如：

```text
Player attacked Goblin and dealt 25 damage.

Player entered tile (3,-1,-2).

Inventory is full.

Weather changed to HeavyRain.

Game saved successfully.

Mission completed.

Random value generated successfully.
```

涉及具体数值、坐标、物品或目标时，应优先使用稳定 ID 或统一英文名称，避免同一对象在不同模块中出现多种写法。

---

## 4. 推荐日志功能

整个项目统一维护以下日志功能。新增功能前应先确认现有分类无法表达该业务，避免产生大量含义重叠的日志类别。

| 功能 | 说明 |
| --- | --- |
| `System` | 系统启动、关闭及其他生命周期行为。 |
| `Player` | 玩家加入、离开及角色相关行为。 |
| `Battle` | 战斗开始、攻击、伤害及战斗结算。 |
| `Move` | 玩家移动、位移及位置变化。 |
| `Map` | 地图生成、区域变化及地块状态。 |
| `Item` | 物品获取、使用、丢弃及背包操作。 |
| `Equip` | 装备穿戴、卸下、替换及装备效果。 |
| `Level` | 经验变化、升级及属性点分配。 |
| `Quest` | 使命、任务及相关进度变化。 |
| `Weather` | 天气、昼夜及环境状态变化。 |
| `Hand` | 手牌、策略牌及弃牌行为。 |
| `Npc` | NPC、怪物及其他非玩家角色。 |
| `Shop` | 商店、购买、出售及服务消费。 |
| `Random` | 随机流、随机判定及随机结果记录。 |
| `Save` | 存档创建、写入及保存结果。 |
| `Load` | 存档读取、恢复及校验结果。 |
| `Network` | 局域网连接、同步及断线处理，作为后续联机功能预留。 |

日志功能名称属于公共枚举。任何新增、删除或重命名都应作为日志规范变更统一处理。

## 5. 日志输出示例

玩家攻击：

```text
[2026-08-01 12:30:15.021][INFO ][Runze  ][Battle ][BattleService] Player attacked Goblin and dealt 25 damage.
```

玩家移动：

```text
[2026-08-01 12:30:18.447][INFO ][Runze  ][Move   ][MoveController] Player entered tile (3,-1,-2).
```

获得物品：

```text
[2026-08-01 12:30:33.125][INFO ][Runze  ][Item   ][InventoryService] Player obtained IronSword.
```

角色升级：

```text
[2026-08-01 12:31:02.531][INFO ][Runze  ][Level  ][LevelService] Player reached level 5.
```

天气变化：

```text
[2026-08-01 12:31:18.904][INFO ][-------][Weather][WeatherManager] Weather changed to HeavyRain.
```

NPC 刷新：

```text
[2026-08-01 12:31:40.128][INFO ][-------][Npc    ][NpcSpawner] Merchant spawned successfully.
```

随机结果：

```text
[2026-08-01 12:32:05.224][DEBUG][Runze  ][Random ][RandomService] Generated random value 87.
```

游戏存档：

```text
[2026-08-01 12:32:44.561][INFO ][-------][Save   ][SaveManager] Game saved successfully.
```

装备失败：

```text
[2026-08-01 12:33:10.741][ERROR][Runze  ][Equip  ][InventoryService] Failed to equip item because the slot is occupied.
```

## 6. 日志使用规范

整个项目统一遵循以下规范：

1. 所有正式日志必须通过统一日志工具输出。
2. 禁止在业务代码中直接使用 `console.log()` 等方式记录正式日志。
3. 日志等级应准确反映事件的重要程度。
4. 日志内容统一使用英文描述。
5. 日志内容应完整、简洁且含义明确。
6. 固定宽度字段统一左对齐，并在右侧补充空格。
7. 与玩家无关的日志对象统一使用 `[-------]`。
8. 日志模块统一使用稳定的类名、模块名或服务名。
9. 关键业务结果应输出 `INFO` 日志，调试信息使用 `DEBUG` 或 `TRACE`，异常情况使用 `WARN` 或 `ERROR`。
10. 不得随意修改日志字段顺序、字段宽度或公共日志功能名称。
11. 不得通过日志泄露其他玩家的隐藏信息或能够预测后续随机结果的数据。
12. 日志记录失败不能改变已经确定的游戏业务结果，但必须通过降级机制保留错误信息。

日志数量应保持适度。高频算法内部过程默认使用 `TRACE` 或 `DEBUG`，避免在正常运行时产生大量无意义日志。

---

## 7. 固定字段宽度

| 字段 | 宽度 | 对齐方式 |
| --- | --- | --- |
| 时间 | 固定格式 | 左对齐 |
| 日志等级 | `5` | 左对齐 |
| 日志对象 | `7` | 左对齐 |
| 日志功能 | `8` | 左对齐 |
| 日志模块 | 不限 | 左对齐 |
| 日志内容 | 不限 | 正常输出 |

固定宽度由统一日志工具负责处理。业务模块只需提供原始字段值，不应自行补空格、截断名称或添加中括号。

---

## 8. 最终标准格式

整个项目所有可读日志统一遵循以下格式：

```text
[2026-08-01 12:30:15.021][INFO ][Runze  ][Battle ][BattleService] Player attacked Goblin and dealt 25 damage.
```

该格式具有以下特点：

* 固定宽度并保持纵向对齐，便于人工阅读；
* 信息完整，包含时间、等级、对象、功能、模块及具体内容；
* 日志内容使用英文，保证跨平台检索一致性；
* 便于搜索、过滤、统计和后期维护；
* 可与结构化日志、游戏序列号及存档信息建立关联；
* 能够为问题定位和游戏复盘提供统一基础。

日志格式一旦进入正式使用，应保持向后兼容。若后续需要增加字段，应优先通过结构化数据扩展，而不是随意修改当前可读日志格式。
