# 《开天辟地之大地的裂变》事件设计规范

## 1. 设计目标

事件设计规范用于统一管理游戏中所有随机事件的数据结构、表现形式与结算规则。

所有新增事件均应遵循本规范进行设计，避免不同事件之间出现数据结构不一致、结算逻辑混乱或难以维护的问题。

事件设计应遵循以下基本原则：

* 统一结构：所有事件使用相同的数据格式进行配置。
* 统一结算：不同事件共享同一套事件触发与执行流程。
* 配置优先：尽可能通过标准效果与条件配置事件，而不是为每个事件单独编写逻辑。
* 便于扩展：新增事件原则上无需修改事件系统框架。

配置优先并不意味着所有复杂规则都必须强行写成配置。当某项内容确实需要新的通用能力时，应先判断该能力是否可以服务多项事件，再将其扩展为标准条件或标准效果；不应为单个事件添加只能使用一次的专属代码分支。

事件设计的核心目标可以概括为：

**用统一、可验证的结构承载丰富事件，而不是用大量例外逻辑堆砌随机内容。**

---

## 2. 基础信息规范

每个事件均应具有完整的基础信息，用于事件管理、候选筛选、随机抽取、结算与界面展示。

### 2.1 基础字段

每项事件建议包含以下字段：

| 字段 | 说明 |
| --- | --- |
| `eventId` | 全局唯一标识，仅供配置、日志与程序管理使用。 |
| 事件名称 | 玩家看到的正式事件名称。 |
| 事件类别 | 普通、命运、遭遇、世界、灾难、奇遇、祝福、诅咒或彩蛋。 |
| 稀有度 | 决定事件的基础抽取权重等级。 |
| 事件描述 | 向玩家展示的背景、处境与必要信息。 |
| 事件标签 | 用于检索、事件池组织与条件筛选的标准化标签。 |
| 重复规则 | 可重复、每名玩家一次或整局唯一。 |
| 冷却规则 | 再次进入候选集合前需要等待的回合数或条件，可选。 |
| 触发条件 | 事件进入候选集合必须满足的条件。 |
| 事件选项 | 玩家可以选择的行动及其条件，可选。 |
| 事件效果 | 无选项事件的直接效果，或各选项对应的效果列表。 |
| 持续规则 | 持续类型、结算时机与结束条件；即时事件不填写。 |

其中，`eventId` 不直接向玩家展示。一经进入正式配置，不应因名称、文本或平衡调整而随意修改，以保证前置事件、日志与存档引用保持稳定。

“是否可重复”与“是否唯一”不建议分别使用两个布尔字段保存，否则可能出现同时为真或同时为假的矛盾配置。统一的重复规则应明确表达以下三种状态：

| 重复规则 | 说明 |
| --- | --- |
| 可重复 | 满足冷却与其他条件后可以再次触发。 |
| 每名玩家一次 | 每名玩家在一局中最多触发一次。 |
| 整局唯一 | 本局游戏中无论由谁触发，最多只发生一次。 |

### 2.2 信息完整原则

事件配置必须能够回答以下问题：

* 什么情况下可以进入候选集合。
* 由什么行为或世界变化触发。
* 哪些玩家能够看到事件信息。
* 哪名玩家负责作出选择。
* 每个选项需要满足什么条件。
* 事件将影响哪些目标。
* 效果按照什么顺序执行。
* 持续效果何时结算与结束。
* 重复触发时如何处理。

如果任意问题无法从标准字段、通用规则或事件文本中得到答案，该事件不能进入正式事件库。

### 2.3 统一设计模板

新增事件时，建议使用以下模板：

```text
事件名称：
事件标识：
事件类别：
稀有度：
核心定位：

事件描述：
事件标签：
重复规则：可重复 / 每名玩家一次 / 整局唯一
冷却规则：

触发来源：
触发条件：
作用范围：

事件选项：
事件效果：
效果顺序：

持续类型：即时 / 固定回合 / 条件结束 / 世界结束 / 永久
结算时机：
结束条件：
重复触发处理：

所属事件池：
备注：
```

“核心定位”应使用一句话说明该事件希望创造的处境或决策。“所属事件池”用于内容管理，不应替代事件自身的触发条件。

## 3. 触发条件规范

事件可以根据不同条件进入候选事件集合。

触发条件包括但不限于：

* 当前地图区域。
* 当前地形。
* 天气状态。
* 昼夜状态。
* 玩家等级。
* 玩家身份或转职。
* 玩家种族。
* 玩家信仰。
* 当前任务与任务阶段。
* 当前副本。
* 当前世界状态。
* 是否拥有指定道具或装备。
* 是否满足指定资源数量。
* 是否已经完成前置事件。
* 是否尚未触发互斥事件。

同一条件组内存在多个触发条件时，默认必须同时满足全部条件，事件才能进入候选集合。

如果事件需要表达“满足其中任意一项即可”，必须使用明确的条件分组进行配置，不能依赖事件描述中的自然语言临时判断。

触发条件应符合以下要求：

* 条件必须能够由现有系统明确判断。
* 条件应描述当前事实，不应直接执行任何效果。
* 隐藏条件可以不向玩家公开，但必须能够被系统验证。
* 不满足条件的事件不得通过提高权重进入候选集合。
* 没有特殊要求时，事件默认不存在额外触发限制。

事件标签不能单独代替触发条件。标签用于组织与检索，真正决定事件是否合法出现的内容必须写入触发条件。

---

## 4. 效果设计规范

事件效果是事件的核心内容。

为了降低系统复杂度，所有事件效果应由若干标准效果组合完成，而不是为每个事件设计独立结算逻辑。

### 4.1 基础效果类型

建议支持以下基础效果类型：

| 效果类型 | 示例 |
| --- | --- |
| 资源状态变化 | 恢复或扣除当前生命值、当前灵力值。 |
| 成长资源变化 | 获得或失去经验值、元宝及其他合法成长资源。 |
| 属性修饰 | 在指定时间内增加或降低基础属性、派生属性。 |
| 物品变化 | 获得或失去材料、图纸、装备、道具或策略牌。 |
| 状态变化 | 添加、刷新或移除祝福、诅咒、中毒等状态。 |
| 战斗相关 | 生成敌人、创建遭遇并进入战斗流程。 |
| 地图变化 | 开启道路、封锁区域、改变地块状态或生成特殊地点。 |
| NPC 变化 | 刷新 NPC、改变 NPC 状态或开启特殊交互。 |
| 世界变化 | 改变天气、昼夜、裂变值或其他世界状态。 |
| 任务变化 | 生成任务、提供线索或推进任务阶段。 |
| 移动变化 | 传送、强制移动或改变角色所在位置。 |
| 信息获取 | 揭示地图、天气、宝藏、身份线索或其他情报。 |

复杂事件可以由多个基础效果组合形成，但所有效果必须服务于同一个事件主题。

### 4.2 效果字段

每个基础效果至少应明确：

* 效果类型。
* 作用目标。
* 操作方式。
* 数值或资源内容。
* 执行顺序。
* 条件不足或执行失败时的处理方式。

效果按照配置顺序执行。后续效果依赖前置结果时，必须明确写出依赖关系，不得通过隐藏顺序产生不同结果。

如果一组效果必须全部成功或全部失败，应明确标记为整体结算。未标记整体结算的效果，也必须说明某一步失败后是停止后续效果，还是跳过失败项并继续执行。

### 4.3 系统职责边界

事件配置只负责声明要产生的结果，具体规则由对应系统执行。

例如：

* 生命值与灵力值变化遵循数值系统的整数与边界规则。
* 临时属性变化通过属性修饰器实现，不直接修改最终属性结果。
* 永久基础属性成长必须调用角色成长规则，不得伪装成永久动态修饰器。
* 战斗胜负与伤害结算由战斗系统负责。
* 任务是否完成由任务系统校验，事件不能绕过条件直接写入完成状态。
* 地图、NPC、天气与昼夜变化由各自系统执行。

事件文本只用于向玩家解释结果，不能作为程序判断效果的唯一依据。

### 4.4 效果复杂度

普通事件通常只包含一个核心结果，必要时可以附带一个紧密相关的效果。

高稀有度事件可以拥有多个连续结果，但应避免：

* 递归触发同一个事件。
* 多个事件之间形成无限循环。
* 一次事件连续生成大量新事件。
* 使用无法追踪来源的隐藏修饰。
* 同时修改过多无关系统。

如果一个事件需要建立大量独立规则才能成立，应将其拆分为事件链、任务或专门的玩法模块。

## 5. 玩家选择规范

部分事件允许玩家作出选择。每个选项应对应明确条件、代价与结果。

常见选择包括：

* 接受或拒绝。
* 战斗或离开。
* 支付资源或放弃奖励。
* 承受伤害或状态以换取奖励。
* 选择一种奖励或发展方向。

事件选项遵循以下规范：

* 普通事件通常不超过 `2` 个选项。
* 特殊事件可以提供更多策略选择，但应控制阅读与结算成本。
* 每个选项均应具有明确的收益、风险与适用场景。
* 不应长期存在不受局势影响的唯一最优选项。
* 不满足条件的选项应明确显示为不可选择，并说明可公开的限制原因。
* 选项确认后，除非事件规则允许响应，否则不能反复撤销与重新选择。

“随机获得一种奖励”属于随机效果，不属于玩家选择。只有玩家能够在多个合法选项之间主动决定时，才应配置为事件选项。

事件可以针对不同身份、转职、种族或信仰提供特色选项，但特色选项不应无条件优于所有通用选项，也不应使其他角色完全无法参与事件。

---

## 6. 持续效果规范

事件可以分为即时事件与持续事件。

持续事件必须明确持续时间、结算时机与结束条件。

| 持续类型 | 说明 |
| --- | --- |
| 即时 | 立即完成结算，不保留事件状态。 |
| 固定回合 | 持续指定回合数，到期后结束。 |
| 条件结束 | 满足明确条件后结束。 |
| 世界结束 | 对应世界事件结束时一并结束。 |
| 永久 | 在本局游戏中持续存在，不会自动结束。 |

持续事件应由统一的持续状态管理流程维护，不允许每项事件自行建立独立计时逻辑。

每项持续事件必须配置：

* 作用对象。
* 开始生效的阶段。
* 重复结算的时机。
* 持续回合数或结束条件。
* 重复触发时覆盖、刷新、叠加或忽略的规则。
* 结束时需要撤销或恢复的状态。

永久事件必须十分稀有，并且只能用于明确改变本局世界状态的内容。永久效果不能以无法移除的动态修饰器形式长期污染角色数值。

---

## 7. 稀有度规范

不同事件拥有不同的基础出现权重。

建议采用以下统一稀有度划分：

| 稀有度 | 建议基础权重 | 说明 |
| --- | ---: | --- |
| 普通 | `100` | 最常见的事件，主要构成日常探索体验。 |
| 稀有 | `40` | 出现频率较低，通常提供更鲜明的选择或结果。 |
| 史诗 | `15` | 能够明显影响玩家、区域或当前局势。 |
| 传说 | `5` | 足以改变游戏节奏，通常具有严格触发条件。 |
| 神话 | `1` | 极少出现，通常影响多个玩家或整个世界。 |

事件抽取使用权重，而不是为每项事件分别配置固定百分比。

某项事件在当前候选集合中的实际概率为：

```text
事件当前权重 ÷ 所有合法候选事件的当前权重总和
```

基础权重可以受到区域、昼夜、天气、游戏阶段与近期触发记录影响。权重为 `0` 时，事件本次不参与抽取；权重不得为负数。

稀有度描述事件出现频率与影响范围，不直接代表事件一定是正面结果，也不代表高稀有度事件可以破坏基础规则。

神话事件属于极低频扩展内容。基础事件库可以暂不配置神话事件，待世界事件与整体平衡稳定后再逐步加入。

## 8. 平衡设计原则

事件平衡应从出现频率、触发阶段、作用范围、风险、收益与玩家应对能力等多个方面共同判断。

事件设计应遵循以下原则：

* 大多数事件只影响当前玩家或当前区域。
* 世界级事件应保持较低出现频率，并为玩家提供预警或应对机会。
* 正面事件与负面事件的总体期望应保持相对平衡，而不是简单追求数量完全相同。
* 普通事件不得直接决定胜负或使玩家无条件退出游戏。
* 高收益事件应伴随相应风险、条件、成本或后续影响。
* 永久效果应十分稀有，并优先作用于世界状态而不是角色基础属性。
* 玩家应尽量拥有自主选择权，而不是完全被动接受重大结果。
* 身份、转职、种族与信仰可以拥有更容易触发的特色事件，但不应完全排斥其他事件。
* 同一事件不能同时成为最高收益、最低风险与最高出现频率的选择。

平衡正面与负面事件时，应考虑实际影响程度。一个足以使玩家失去主要资源的负面事件，不能仅通过一个提供少量元宝的正面事件进行数量抵消。

游戏前期应减少无法应对的高惩罚事件，后期则可以随着玩家装备、资源与信息能力提升，逐步开放影响范围更大的事件。

## 9. 数据组织建议

为了方便维护，所有事件均应采用资源配置方式进行管理，并在游戏启动或资源加载阶段完成校验。

事件定义与事件池应分别管理：

```text
events/
├── definitions/
│   ├── common/
│   ├── destiny/
│   ├── encounter/
│   ├── world/
│   ├── disaster/
│   ├── adventure/
│   ├── blessing/
│   ├── curse/
│   └── easter_egg/
└── pools/
    ├── regions/
    ├── maps/
    ├── npc/
    ├── weather/
    ├── dungeons/
    └── world/
```

`definitions` 按事件主要类型保存事件本体，`pools` 负责引用可以在不同区域、场景与触发来源中出现的事件。事件池只保存事件引用与必要的池内权重修正，不复制完整事件定义。

程序负责：

* 加载并校验事件资源。
* 根据触发来源确定候选事件池。
* 合并候选事件并按照 `eventId` 去重。
* 根据条件筛选合法事件。
* 根据当前权重随机抽取事件。
* 执行统一的选择、响应与结算流程。
* 管理事件冷却、唯一性与持续状态。
* 按照《14-日志系统》记录事件触发与结算日志，并避免泄露未公开选项及隐藏结果。

事件配置负责：

* 描述事件基础信息。
* 声明触发条件与重复规则。
* 定义事件选项与标准效果。
* 配置持续规则与结束条件。
* 指定基础权重与所属事件池。

新增普通事件时，仅需新增对应事件定义并将其加入合法事件池，无需修改事件系统核心代码。

### 9.1 配置校验

事件资源加载时应至少检查：

* `eventId` 是否存在且全局唯一。
* 事件类别、稀有度与标签是否合法。
* 事件池引用的事件是否存在。
* 触发条件与基础效果类型是否受到支持。
* 权重是否为非负整数。
* 选项标识是否在事件内唯一。
* 持续事件是否配置结算时机与结束条件。
* 前置事件与后续事件是否存在循环依赖。
* 整局唯一事件是否配置了与其冲突的重复规则。

存在结构错误或无法解析的事件时，应阻止该事件进入正式事件池并记录明确错误，不能在运行过程中依赖临时默认值猜测设计意图。

## 10. 设计原则总结

事件设计应始终围绕探索、选择与未知展开。

事件既是玩家获得资源与成长机会的重要途径，也是推动世界不断变化的重要动力，但不能替代地图、战斗、角色、任务等系统自身的职责。

优秀的事件应具备以下特点：

* 容易理解。
* 容易结算。
* 易于维护。
* 支持扩展。
* 风险与收益并存。
* 与地图、角色、任务、战斗等系统形成明确联动。
* 每次触发都能为玩家带来符合当前场景的游戏体验。

通过统一的数据结构、标准效果、条件筛选与持续管理规范，可以在保持系统稳定的同时持续扩充事件内容，为游戏提供长期的新鲜感与可玩性。
