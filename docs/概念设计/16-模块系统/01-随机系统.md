# 《开天辟地之大地的裂变》随机系统设计

## 1. 设计目标

随机系统用于为游戏中的各种玩法提供统一、稳定且可复现的随机能力，包括地图生成、战斗、掉落、事件、天气及其他所有涉及随机结果的功能。

本系统遵循以下设计原则：

* 所有影响游戏结果的随机行为统一管理，不允许业务模块自行生成随机数。
* 每局游戏只生成一次主随机种子，保证整局随机过程可以复现。
* 不同业务模块使用相互独立的随机流，避免随机调用彼此干扰。
* 随机算法与业务逻辑解耦，便于维护、测试与扩展。
* 随机结果由服务器权威生成，客户端不能自行决定游戏结果。
* 支持联机同步、存档恢复、游戏回放、问题调试与日志记录。

随机系统只负责根据明确的输入产生随机结果，不负责决定何时随机、候选内容是否合法，以及随机结果将产生何种业务效果。

例如，事件系统负责筛选当前可以触发的事件并提供权重，随机系统只负责从合法候选集合中抽取一项；战斗系统负责提供目标最终闪避率，随机系统只负责完成对应的闪避判定。

随机系统的核心职责可以概括为：

**统一产生随机结果，完整记录随机过程，但不替代任何业务系统作出规则判断。**

---

## 2. 总体架构

随机系统采用“主种子 + 多随机流 + 作用域子流”的设计方式。

游戏开始时，由服务器生成本局唯一的安全随机主种子（Master Seed）。随机管理器根据主种子和稳定的随机流标识，为不同业务模块派生相互独立的随机流（Random Stream）。

当同一模块包含多个彼此独立的实例时，可以继续按照稳定的作用域标识派生子流。例如，不同战斗、不同宝箱和不同副本可以拥有各自的作用域子流。

整体结构如下：

```text
安全随机源
    │
    ▼
主随机种子（每局唯一）
    │
    ▼
RandomManager
    │
    ├── 地图随机流
    ├── 世界事件随机流
    ├── 天气随机流
    ├── 使命随机流
    ├── 战斗随机流
    │       ├── 战斗 A 子流
    │       └── 战斗 B 子流
    └── 掉落随机流
            ├── 宝箱 A 子流
            └── 敌人 B 子流
```

所有影响玩法的随机结果均来源于对应随机流，不允许直接调用系统随机函数。

这种结构可以保证：

* 一个模块增加随机调用时，不会改变其他模块的随机序列。
* 一场战斗增加暴击判定时，不会影响另一场战斗、后续天气或物品掉落。
* 相同主种子、规则版本与输入顺序可以复现相同结果。
* 新增随机模块时，只需注册新的稳定随机流，无需修改已有业务逻辑。

### 2.1 服务器权威

所有影响游戏状态的随机结果均由服务器生成并确认。

客户端负责发送随机请求所需的业务信息，并接收服务器已经确认的结果，不能自行推进权威随机流。多个客户端也不能分别生成结果后再进行比较或投票。

客户端可以为粒子、音效、界面抖动等纯表现内容使用本地随机，但这些结果必须满足以下条件：

* 不改变任何游戏状态。
* 不影响玩家能够获得的信息。
* 不参与战斗、掉落、事件或其他规则结算。
* 不需要进入权威随机日志与游戏回放。

### 2.2 版本约束

随机结果不仅取决于种子，还取决于随机算法、配置内容与调用顺序。

因此，每局游戏必须同时记录：

* 随机算法标识与版本。
* 游戏规则版本。
* 参与随机的配置版本。
* 主种子或其受保护引用。
* 各随机流标识与当前状态。

算法或配置发生变化后，即使使用相同主种子，也不保证与旧版本产生相同结果。回放旧对局时，应加载该对局记录的对应版本，而不是直接使用当前版本重新计算。

## 3. 主随机种子

每局游戏开始时，只生成一次主随机种子。

主随机种子由服务器使用密码学安全随机源生成，并作为本局所有权威随机流的唯一根来源。

主随机种子的职责包括：

* 保证不同对局拥有不同的随机序列。
* 为各业务随机流与作用域子流派生子种子。
* 支持存档恢复、游戏回放和问题复现。
* 支持随机过程校验与日志关联。
* 防止客户端在游戏过程中预测后续随机结果。

游戏过程中不能重新生成或替换主随机种子。玩家断线重连、服务器恢复存档或回放暂停后继续时，均应恢复原主种子与随机流状态，而不是建立新的随机序列。

### 3.1 生成时机

主种子应在以下条件全部确定后生成并锁定：

* 对局已经创建。
* 游戏模式与规则版本已经确定。
* 参与玩家已经完成确认。
* 服务器准备开始世界初始化。

主种子生成后，地图初始化、出生布局、使命生成及其他开局随机行为均从对应随机流中获得结果。

### 3.2 安全与公开

主种子属于服务器权威数据。

对局进行过程中，客户端不能获得能够推导后续随机结果的完整主种子。服务器不得将主种子写入普通可读日志，也不能发送给无权访问的客户端。

游戏结束后，是否公开主种子由对局模式决定。需要支持赛后复盘、好友验证或调试时，可以公开种子及必要版本信息；竞技性模式可以继续保留受保护记录，只允许服务器验证。

### 3.3 子种子派生

各随机流的子种子应通过稳定的种子派生函数获得，而不是依次从主随机流抽取。

推荐派生输入如下：

```text
子种子 = SeedDeriver(
    主种子,
    随机算法版本,
    随机流类型,
    作用域标识
)
```

随机流类型与作用域标识必须使用稳定标识，不能使用本地化名称、对象内存地址、当前时间或不稳定的集合遍历顺序。

派生新的随机流不会推进其他随机流的状态。

## 4. 随机流

随机流（Random Stream）是随机系统最核心的组成部分。

每个随机流负责一类相对独立的随机计算。建议至少划分以下随机流：

| 随机流 | 主要职责 |
| --- | --- |
| 地图随机流 | 地图初始化、资源分布与随机地形内容。 |
| 战斗随机流 | 闪避、暴击及其他明确的战斗随机判定。 |
| 掉落随机流 | 敌人掉落、宝箱内容与个人奖励品质。 |
| 事件随机流 | 合法事件池中的事件抽取与事件选项随机结果。 |
| 天气随机流 | 天气类型、持续时间与合法天气变化。 |
| NPC 随机流 | NPC 生成、行为选择与随机商品。 |
| 任务随机流 | 普通任务候选目标与任务奖励。 |
| 使命随机流 | 五类隐藏使命的权重抽取与重塑替换。 |
| 牌组随机流 | 手牌、扑克牌及其他牌组的洗牌与抽取顺序。 |
| 轮回随机流 | 复活、中途加入、随机出生与相关 D20 判定。 |
| 契约随机流 | 神鬼契约的隐藏触发、候选抽取与私有机会生成。 |

不同随机流之间完全独立。

例如，战斗系统新增一次暴击判定，不会改变后续天气、事件或掉落结果；调整宝箱开启顺序，也不会改变地图初始化时已经确定的资源分布。

### 4.1 作用域子流

仅按照模块划分随机流，仍可能使同一模块中的多个实例互相影响。

因此，对于能够独立识别的业务实例，建议使用作用域子流：

* 每场战斗使用 `combatId` 派生战斗子流。
* 每个宝箱使用 `containerId` 派生掉落子流。
* 每个副本使用 `dungeonId` 派生副本子流。
* 每名玩家的个人使命使用 `playerId` 派生使命子流。
* 每个独立牌组使用 `deckId` 派生牌组子流。
* 每次死亡或中途加入使用 `playerId` 与 `reincarnationId` 派生轮回子流。
* 每次神鬼契约机会使用 `playerId` 与 `contractOpportunityId` 派生契约子流。

作用域标识必须在本局中唯一且稳定。对象显示名称不能作为唯一标识。

并非每次随机调用都需要创建新的子流。连续属于同一业务过程的多次判定，应复用同一个作用域子流并按照确定顺序推进。

### 4.2 随机流状态

每个随机流至少应维护：

| 状态 | 说明 |
| --- | --- |
| 流标识 | 随机流类型与作用域标识。 |
| 算法版本 | 当前流使用的确定性随机算法版本。 |
| 初始子种子 | 由主种子派生的流种子。 |
| 当前状态 | 用于继续产生后续随机结果的内部状态。 |
| 调用序号 | 当前随机流已经完成的权威调用次数。 |

存档时必须保存足以恢复每条已创建随机流的状态。读取存档后，下一次随机调用应与未中断运行时完全一致。

### 4.3 调用顺序

同一随机流内的调用顺序会影响后续结果。

业务系统必须在规则中明确随机调用发生的结算节点，并按照稳定顺序处理多个目标。不能依赖客户端响应先后、网络到达顺序或无序集合遍历顺序决定随机调用顺序。

取消的操作原则上不应消耗随机结果。只有业务条件已经验证、随机请求正式进入权威结算后，才允许推进对应随机流。

## 5. 随机系统职责

随机系统只负责提供通用随机能力。

### 5.1 基础能力

随机系统应支持以下标准能力：

| 随机能力 | 说明 |
| --- | --- |
| 整数随机 | 在明确的整数区间内生成结果。 |
| 整数比例判定 | 根据 `rate / scale` 形式的整数比例返回成功或失败。 |
| 权重随机 | 根据非负整数权重从合法候选集合中选择一项。 |
| 列表选择 | 从非空列表中等权选择一项或多项。 |
| 洗牌 | 使用确定性洗牌算法重新排列列表。 |
| 随机排序 | 通过洗牌结果获得随机顺序，不使用随机比较函数排序。 |

业务系统不得自行实现随机算法，也不得直接创建随机对象。所有随机需求均通过统一随机接口完成。

### 5.2 接口语义

所有随机接口必须明确输入、输出与边界规则，不能由调用方自行猜测。

建议统一采用以下语义：

* `nextInt(minInclusive, maxExclusive)` 使用左闭右开区间，结果满足 `minInclusive <= result < maxExclusive`。
* `roll(rate, scale)` 从 `[0, scale)` 中生成整数；当结果小于 `rate` 时判定成功。
* 空候选列表不能执行随机选择，应返回明确的业务错误。
* 权重必须为非负整数，负数权重属于非法配置。
* 权重为 `0` 的候选项不参与抽取。
* 所有候选项权重均为 `0` 时，抽取不能继续。
* 概率在进入随机系统前，必须按照数值系统限制在合法范围内。
* 多项选择必须明确是否允许重复抽取，以及每次抽取后是否移除候选项。

其中，`scale` 必须使用大于 `0` 的整数。百分制判定可使用 `scale = 100`，万分制判定可使用 `scale = 10000`。当 `rate = 0` 时必定失败，当 `rate = scale` 时必定成功。

所有权威玩法概率与权重均使用整数表示，例如百分制、千分制或万分制。随机系统不提供浮点随机接口，概率判定也不需要先计算浮点商值，从而避免不同运行环境中的浮点误差改变判定结果。

随机系统不会自动修正非法业务输入。输入不合法时，应拒绝执行并记录错误，不能静默替换为另一个随机规则。

### 5.3 职责边界

随机系统与业务系统的职责划分如下：

| 内容 | 负责系统 |
| --- | --- |
| 筛选当前合法事件 | 事件系统 |
| 从合法事件中按权重抽取一项 | 随机系统 |
| 计算角色最终闪避率 | 数值系统与战斗系统 |
| 根据最终闪避率完成判定 | 随机系统 |
| 决定敌人可以掉落哪些物品 | 掉落系统 |
| 从合法掉落池中生成结果 | 随机系统 |
| 计算角色最终幸运值 | 数值系统 |
| 根据规则使用幸运值修正个人收益权重 | 随机系统 |
| 应用随机结果并改变游戏状态 | 对应业务系统 |

随机系统返回结果后，由发起请求的业务系统负责验证上下文、应用效果并完成最终结算。

## 6. 幸运值

幸运值（Luck）属于角色派生属性，由数值系统计算最终有效值。

幸运值不会改变主种子、随机流状态或随机算法，也不会要求重新抽取已经产生的结果。它只在具体业务规则明确允许时，修正当前玩家个人收益候选项的权重。

### 6.1 允许影响的内容

幸运值可以影响以下个人收益内容：

* 提高个人掉落中稀有物品的相对权重。
* 提高个人宝箱奖励的品质倾向。
* 提高个人隐藏奇遇进入候选池后的抽取权重。
* 提高面向个人的特殊商品出现权重。
* 提高普通任务个人额外奖励的出现权重。

幸运值是否参与某项随机行为，必须由对应业务规则明确声明。没有声明时，默认不受幸运值影响。

### 6.2 禁止影响的内容

幸运值不影响以下公共规则与基础随机行为：

* 世界事件类型及其出现顺序。
* 天气变化。
* 地图生成、资源总体分布与出生布局。
* 手牌、扑克牌及其他公共牌组的洗牌与抽取顺序。
* 战斗闪避、暴击及其他已经拥有独立概率属性的基础判定。
* 其他玩家的掉落、宝箱、事件与任务结果。
* 使命生成与使命重塑。
* 神鬼契约的触发机会与契约内容。

因此，幸运值影响的是角色的个人收益倾向，而不是整个世界的随机规则。

### 6.3 权重修正

幸运值修正应作用于业务系统提供的基础权重，并在随机抽取前得到最终整数权重。

```text
基础候选权重
      │
      ▼
业务规则确认是否允许幸运修正
      │
      ▼
读取角色最终幸运值
      │
      ▼
LuckModifierPolicy 计算最终权重
      │
      ▼
随机系统按最终权重抽取结果
```

幸运值修正必须遵循以下原则：

* 只修改允许受到幸运影响的候选项权重。
* 不直接指定某项结果必然出现。
* 不生成候选池中原本不存在的奖励。
* 不使任何最终权重变为负数。
* 修正规则由统一配置维护，不由装备、事件或掉落项自行实现。
* 相同输入、相同随机流状态与相同幸运值必须得到相同结果。

幸运值提高稀有结果的相对机会时，应同时明确普通结果权重如何变化，保证最终权重总量与概率分布可以验证。

## 7. 模块划分

随机系统统一放置于 `random` 模块中进行管理。

推荐结构如下：

```text
random/
├── core/
│   ├── RandomManager
│   ├── RandomStream
│   ├── RandomStreamType
│   ├── SeedGenerator
│   └── SeedDeriver
├── service/
│   ├── CombatRandomService
│   ├── LootRandomService
│   ├── EventRandomService
│   ├── WeatherRandomService
│   ├── QuestRandomService
│   ├── MissionRandomService
│   ├── DeckRandomService
│   ├── ReincarnationRandomService
│   ├── DivineContractRandomService
│   └── MapRandomService
├── policy/
│   ├── WeightedRandomPolicy
│   ├── ProbabilityPolicy
│   ├── LuckModifierPolicy
│   └── ShufflePolicy
└── model/
    ├── RandomContext
    ├── RandomResult
    ├── WeightedItem
    └── RandomAuditRecord
```

### 7.1 `core` 层

`core` 层负责随机系统的底层确定性能力：

* 生成并保护主随机种子。
* 派生模块随机流与作用域子流。
* 管理随机算法版本。
* 维护和恢复随机流状态。
* 提供基础确定性随机序列。

业务模块不能直接依赖具体随机算法实现，只能通过稳定接口请求随机结果。

### 7.2 `service` 层

`service` 层为不同业务模块提供语义明确的随机服务。

例如，`CombatRandomService` 可以提供闪避与暴击判定，`LootRandomService` 可以提供掉落池抽取，`DeckRandomService` 可以提供确定性洗牌。

随机服务只封装对应业务的随机请求，不负责计算伤害、创建物品、执行事件或改变牌组以外的业务状态。

### 7.3 `policy` 层

`policy` 层负责可复用的随机策略，包括：

* 权重归一与权重抽取。
* 概率边界与概率判定。
* 幸运值权重修正。
* 确定性洗牌。

策略应尽量无状态，其结果只依赖明确输入和调用方提供的随机流。

### 7.4 `model` 层

`model` 层负责随机请求、结果与审计上下文的数据结构。

其中，`RandomContext` 应包含业务来源、流类型、作用域标识与调用原因；`RandomResult` 应保存可供业务系统使用的结果；`RandomAuditRecord` 应提供随机流、调用序号、输入摘要、结果及算法版本等最小审计信息。

随机系统只产生随机审计数据，不直接创建或写入日志文件。服务端编排层负责按照《15-日志系统》将允许公开的摘要写入 `Random` 类日志，并将需要用于存档恢复的随机流状态保存至权威状态或存档。

随着后续功能增加，可以继续扩展新的随机服务、策略与流类型，而无需修改已有业务模块。

## 8. 设计原则

随机系统遵循以下原则：

单一主种子原则

每局游戏只生成一次主随机种子，后续随机能力全部由该种子派生。

随机流隔离原则

不同业务模块和独立业务实例使用稳定的随机流或作用域子流，避免随机调用互相影响。

服务器权威原则

所有影响游戏状态的随机结果由服务器生成并确认，客户端不自行推进权威随机序列。

统一接口原则

业务模块不得自行创建随机对象或实现随机算法，所有随机需求通过统一接口完成。

职责分离原则

业务系统负责候选内容、合法条件和结果应用，随机系统只负责从合法输入中产生结果。

幸运边界原则

幸运值只修正明确允许的个人收益权重，不改变随机算法，不干预公共世界规则和基础战斗判定。

可复现原则

随机算法版本、配置版本、随机流状态与调用顺序均应进入权威存档或审计记录，使存档、回放和调试能够恢复相同结果。普通文本日志只记录必要摘要，不能作为随机流状态的唯一保存位置。

失败不消耗原则

业务条件未通过或随机请求被取消时，不推进权威随机流，也不产生可被后续业务使用的结果。

日志可追踪原则

每次权威随机调用均应能够关联游戏局 ID、业务来源、随机流、调用序号、输入摘要与结果，并通过统一日志工具记录允许公开的摘要，但不得在对局过程中向客户端或普通 `latest.log` 泄露能够预测后续结果的信息。

通过统一的种子派生、随机流隔离与服务器权威管理，可以有效降低各业务模块之间的耦合程度，提高联机同步的稳定性，并为数值平衡、存档回放、问题调试与后续功能扩展提供可靠基础。
